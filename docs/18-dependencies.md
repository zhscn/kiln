# 18 依赖追踪（M6.4）

**状态**：在 image 里求值的定义已有依赖追踪（2026-11）。AOT 编出的模块还没有。

这是 [13](13-modern-practices.md) §2 的第一步，也是 [16](16-editor.md) §5.1 的前提。以前在活 image 里重定义宏之后，已经编好的使用者仍按旧的展开运行，要靠用户自己重新求值。现在在 image 里求值的定义会记下编译期用到的定义；其中之一被重新定义时，依赖它的定义会自动重新求值。

## 1. 决定

- **粒度是定义**：`eval` 拿到的一个定义形式（`defun`、`defmacro`、`defmethod` 等，名字的规则同 [17](17-debugging.md) §2.1 的 `definition-name`），是一个单位。宏展开结果里的定义（例如用户的定义宏展开成的 `progn` 里的 `defun`）各自是一个单位。不是定义的顶层形式（REPL 里的表达式）只运行一次，不记录。
- **自动重新求值**：只用于再求值一次的效果只是替换它所定义的东西的定义：`defun`、`defmacro`、`defmethod`、`define-compiler-macro`、`deftype`、`defsetf`、`define-setf-expander`、`define-modify-macro`。重新求值时绑定原来的 `*package*`。
- **其他定义只报告**：`defvar`、`defparameter`、`defclass` 以及用户自己的定义宏等，再求值一次会有别的效果（`defparameter` 会重设值），这类定义发出 `kiln.sys:stale-definition` 警告（style-warning），由用户决定是否重新求值。重新编译出错的定义也报告这个警告，同时保留旧代码。
- **总是传播**：一个定义被求值，就更新依赖它的定义，即使新旧定义的源码相同。重新求值一个没变的宏，正好可以用来传播宏展开函数调用的辅助函数的改动（§4）。

## 2. 依赖的种类

依赖用 `(种类 名字)` 表示。CL 包和关键字包的名字不记录，因为重定义它们是未定义行为。

| 键 | 记录的时机 | 失效的时机 |
|---|---|---|
| `(:macro m)` | 展开了全局宏 `m`；或者编译时 `m` 还没有定义（以后的 `defmacro` 会改变这个形式的含义） | `(setf macro-function)`，即每次 `defmacro` |
| `(:inline f)` | 内联展开了 `f` | `f` 有了新的内联展开，或者被声明为 `notinline` |
| `(:setf f)` | 编译了位置 `(f ...)` 的 `setf` | `defsetf`、`define-setf-expander` |
| `(:constant c)` | 引用了常量 `c`（值折叠进了代码） | `defconstant` 改变了它的值（不 `eql`） |

在哪里记录：
- 前端查询全局环境时（`lisp/target/compiler/client.lisp` 的 `run-time-environment`）：Common-boot 展开宏、宏用 `&environment` 调用 `macro-function`，都会经过这里。查到宏、查不到定义、查到常量时记下依赖。
- `front.lisp`：内联展开时（`convert-maybe-inline`）。检查内联函数体里的名字是否被局部遮蔽，这些查询不算依赖。
- image-client 的 `get-setf-expansion`。
- `native-eval` 自己展开顶层宏形式时（定义的宏本身）。

收集器是 `*dependencies*`。只有原生 `eval` 在求值定义时才绑定它，所以交叉编译和 KIR 都不受影响（SBCL 和 kiln 编出的 KIR 仍然相同）。

## 3. 失效和更新

- 重定义点调用 `kiln.kernel::*redefinition-hook*`。kernel 里有三处：`(setf macro-function)`、`%define-setf-expander`、`%define-constant`。前端里有两处，都只在编译进 image 时调用：`note-inline-definition` 和 `notinline` 声明。compiler 模块载入时设置这个钩子（`lisp/target/compiler/dependencies.lisp`）。
- 钩子只把键放进待处理队列。最外层的 `eval` 返回后，再更新依赖这些键的定义：一个 `defmacro` 会在编译期和载入时各通知一次，在编译中途重新编译别的定义也不安全。不在 `eval` 里、也不在编译中时，钩子立即更新。
- 更新的顺序：按定义的先后。被重新求值的定义如果自己也被依赖（宏、内联函数），会通知新的键，接着更新。同一个定义对同一个键在一轮里至多求值一次，所以宏的展开函数互相使用时也会停下来。
- 依赖关系保存在 compiler 模块的全局表里，存 image 时一起保存。每个单位保存它的定义形式、`*package*` 和依赖的键。重新求值会替换原来的记录。

`defconstant` 的展开在载入时也调用 `%define-constant`。原生 `eval` 不执行 `:compile-toplevel` 部分，以前不会经过它。

内联函数表以前每次 `eval` 都重新从宿主的表复制，所以一个 `eval` 里声明的内联函数，下一个 `eval` 看不到。现在 image 里所有的编译会话共用一张表（`*image-inline-functions*`），内联在 image 里才真正可用，也才需要追踪。

## 4. 不追踪的

- **AOT 编出的模块**：kiln 自己的五个模块和测试程序由交叉编译器编译，没有记录。在 image 里重定义 kernel 的宏，kernel 里已经编好的代码不会更新。要支持它，得在 KIR 里记下每个函数的依赖，模块初始化时装进同一张表（[11](11-m5-self-hosting.md) §4.1 的定义表也要这样做）。
- **宏展开函数在展开时调用的函数**：展开函数调用的辅助函数被重新定义后，不会自动更新。重新求值那个宏就会传播（§1）。
- **`compile` 编出的函数**：没有可以重新求值的定义形式。
- **类型**：`typep` 对非标准的类型在运行期按类型缓存（`%typep-cached`），不在编译期展开 `deftype`，不需要追踪。`defstruct` 在运行期还没有实现。CLOS 分派还没有编译期优化（[14](14-performance.md) §3），以后加上时要记 `(:class c)` 一类的依赖。
- **宏改成函数**：`defun` 不清除名字上的宏函数（原来就是这样），这种重定义目前不起作用。

## 5. 接口

- `(kiln.sys:dependents kind name)`：依赖 `(kind name)` 的定义的名字，按定义的先后。
- `(kiln.sys:dependencies name)`：定义 `name` 的依赖。
- `kiln.sys:*recompile-verbose*`：为真时，每次重新求值都在 `*error-output*` 上打印一行，例如 `; compiling USE-TWICE again: the macro TWICE changed`。
- `kiln.sys:stale-definition`：警告，见 §1。

后端协议（[17](17-debugging.md) §4）里，这些警告和打印都进入任务的输出。

## 6. 测试

`tests/m6/co-dependencies` 覆盖以下情况：
- 宏重定义后使用者跟着更新；
- 先用后定义的宏；
- 展开函数里用到别的宏，形成连锁更新；
- 跨 `eval` 的内联函数，包括重定义和直接改 `fdefinition`（后者内联的调用者看不到）；
- 先用位置后定义 `defsetf`；
- 常量改值；
- 只报告的 `defparameter`；
- 重新编译失败时保留旧代码；
- 展开函数互相使用时的终止。

## 7. 参考：Zig 的增量编译

依据 Zig 源码（commit 60635c2bda，2026-11）的阅读，未经运行验证。

- **单位**：`AnalUnit`。种类有：
  - 声明的值（`nav_val`）和声明的类型（`nav_ty`）分开，只用到类型的地方不依赖值；
  - 函数体、`comptime` 块；
  - 类型布局、结构体字段默认值。
- **被依赖者（`Dependee`）**：
  - 源码哈希：函数只哈希原型，所以只改函数体时，调用者不受影响；
  - 声明的值和类型、推导出的错误集、类型布局；
  - 命名空间中的某个名字是否存在（`namespace_name`）。查找失败也记依赖，以后加上这个声明时精确地失效。
  - 依赖以双向链表存放。重新分析一个单位之前，先清掉它的所有依赖（`resetUnit`），连同它的错误和导出一起清。
- **文件改动**：
  - 重新生成 ZIR，按名字对应新旧声明，匿名的按顺序对应，再比较各自的源码哈希；
  - 只是行号变了，只更新调试信息；
  - 对应不上的算"丢失"；
  - 新增和删除的声明按可达性处理，不立即删除；
  - 文件解析失败时整个更新跳过，不做任何失效。
- **传播和提前截断**：
  - 直接依赖者标为"过时"，再往下的标为"可能过时"（PO），每个带一个计数；
  - 单位重新分析后，比较新旧输出：值是 intern 后的索引，O(1) 比较；
  - 输出没变时，就让下游的计数减一，计数归零的 PO 单位不必重新分析，并继续向下传"没变"；
  - 类型布局目前没有截断。
- **顺序**：不做拓扑排序，只从计数为 0 的就绪集合里取单位。分析中需要一个还是 PO 的单位时，就地先把它分析好，宁可多做也不出错。每次更新每个单位至多分析一次。循环依赖会被检测出来，报编译错误；剩下的全是 PO 单位时，整体视为没变。
- **可靠的前提**：
  - 跨声明的信息都经过 Sema 的显式查找；
  - comptime 没有 I/O，`@embedFile` 和 `@import` 也被追踪；
  - 可变的 comptime 状态不能逃出单位。

  即使如此，激活增量编译时，comptime 调用的记忆化也关掉了，因为调用者的依赖记不上。

**对 kiln 的取舍**：

| Zig | kiln |
|---|---|
| PO 计数加提前截断 | 采用。重新求值后比较输出：宏和内联函数比较新的定义形式，函数比较 KIR（确定的），常量用 `eql`。输出没变就不通知下游。这同时解决了 §8 的第二项 |
| 计数为 0 的就绪集合，按需就地更新 | 采用。代替现在的"按定义先后，每个键至多一次"，改为每次更新每个定义至多一次。编译中需要的宏还是 PO 时，先更新它 |
| 名字是否存在的依赖 | 已有雏形：编译时还没定义的名字记成 `(:macro m)`。应拆成单独的种类，普通的 `defun` 也就不必通知 |
| 类型和值分开、原型和函数体分开 | 内联函数的 lambda list 和函数体分开没有意义：调用者把整个函数体展开进来，任何改动都影响调用者。以后有了编译期的 ftype 推导，"签名"可以单独作为依赖 |
| 新旧 ZIR 对应、源码哈希 | 重新载入文件时用：按定义名对应新旧顶层形式，只求值变了的；只是位置变了的，只更新调试信息里的位置；消失的定义报告出来。需要定义表（[11](11-m5-self-hosting.md) §4.1） |
| 解析失败不做失效 | 重新载入文件时，先读完整个文件，读失败就什么都不改 |
| 每个单位的清理表 | 现在只清依赖；以后定义表、who-calls、警告也按单位记，重新求值前一起清 |

CL 和 Zig 的根本差别在可靠性。宏展开函数可以调用任意函数、读特殊变量，CL 的文件是按顺序执行的脚本，所以 kiln 的追踪只能做到尽力而为（§4），不能像 Zig 那样靠限制 comptime 来保证完整。反过来，CL 的全局函数调用经过函数格，替换函数本身就对所有调用者生效。Zig 要靠 GOT 和增量链接器做的那部分，kiln 不需要。

## 8. 待定

- KIR 里的依赖记录（§4 的第一项），和定义表、who-calls 一起做。
- 重新求值没有变化的宏时，是否跳过更新（比较定义形式）。载入大文件时可以省掉重复的编译，但会挡住 §1 的传播用法。
- 内联缓存、编译后的 CLOS 分派等优化做出来以后，它们的假设也要作为依赖记录（[16](16-editor.md) §5.1）。
