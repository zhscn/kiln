# 性能测量

**日期**：2026-11。数字是当时的测量，不随代码更新；同一张表里的前后对比是在同一台机器上测的。要做的优化见 [roadmap.md](../roadmap.md) 的“性能”。

测量显示，基础调用与控制流的差距较小，较大的运行期差距集中在浮点运算、
大整数、多维数组、流和字符串操作。自编译与程序运行分别测量：前者反映开发
迭代成本，后者反映生成代码和库实现的效率。

各节记录特定实现阶段的测量，旧表中的时间和瓶颈不代表后续实现。最新的
cl-bench 结果见“cl-bench 全量复测与 SXHASH”，编译延迟见相应日期的测量小节。

## 测量方法

`bench/compare.lisp` 是一组可移植的 CL 代码，在 kiln 和 SBCL 上运行同样的操作，输出每次操作的纳秒数：
- kiln：复制成 `clos-*.lisp` 交给 `tools/test.sh`，取 AOT 的输出；
- SBCL：`sbcl --script bench/compare.lisp`，默认优化级别，没有类型声明。

几纳秒的项目只能看数量级，SBCL 那边的计时器分辨率是微秒。

剖析的工具：
- kiln 自己的采样分析器和分配分析器（`KILN_PROFILE`，[debugging.md](../design/debugging.md) 的“性能分析器”）；`KILN_FUNCTION_MAP` 给 perf 报告的 AOT 函数换上 Lisp 的名字。
- perf：`kernel.perf_event_paranoid` 为 2 时，只有软件事件（`-e cpu-clock`）能用；设为 1 后，硬件事件和 `-g` 都能用。kiln 的 AOT 代码有帧指针，`perf report --children` 能给出包含时间。
- kiln-cg 的 JIT 设了 `KILN_PERF_MAP=1` 时写出 perf map，perf 能显示 JIT 函数的名字。
- AOT 程序有帧指针，gdb 能回溯。每次 attach 一次 gdb 抽一个调用栈；在同一次 gdb 会话里连续抽样时，进程一直停着，得到的其实是同一个瞬间。
- 函数的标签带名字（[lowering.md](../design/lowering.md)）；标签里没有名字的，从 KIR 里“把哪个函数对象存进哪个符号”可以对回全局函数名。

### CPU、分配与硬件采样（2026-11-10）

在 IR 变量缓冲区采用直接遍历的编译器上，用同一份模块清单、固定 8 GiB 堆
顺序执行三次内置 CPU 采样、两次分配采样和一次 `perf record -F 499 -g`。
内置 CPU 采样每次约 6,600–6,800 个 tick，硬件采样约 3,957 个样本。剖析运行的时间包含分析器开销，不作为提速基准。

| 阶段 | 内置 CPU 占比（三次中位数） | 分配采样权重 |
|---|---:|---:|
| 前端 | 55.50% | 1,528,506,152 B（48.95%） |
| 降级 | 31.92% | 1,438,189,296 B（46.06%） |
| KIR 输出 | 8.52% | 104,352 B |
| 启动、准备及其他 | 4.00% | 155,901,832 B（4.99%） |

阶段按采样栈中 `print-module`、`compile-module`、`front-end` 的归属分类，
和墙钟阶段边界不完全相同。两次分配采样的权重与归因相同，总计约 3.12 GB；
这是分配慢路径按缓冲区消耗加权的估计，不是存活对象大小，也不是逐对象统计。

**已定位的具体路径：**

- **顶层分块存在平方级遍历。** `lisp/lower.lisp` 的
  `compile-toplevel-function` 每处理 16 个形式，都对整个剩余列表调用 `length`，
  形成 O(n² / 16) 的列表扫描。这条直接调用链占内置 CPU 采样约 1.63%。
  外部采样中全部 `length` 的自身周期占比为 4.59%，其中还包含其他调用点，
  不能全部归给顶层分块。优先改成单次顺序分块。
- **reader 的协议成本高。** 顶层读入链约占内置 CPU 的 33.52%；其中单参数和
  多参数分派闭包自身占整轮采样约 5.4% 和 3.7%（首轮）。典型路径是
  `read-char` / `peek-char` → `stream-read-char :around` → 文件流方法 →
  槽访问器分派。文件流已有缓冲和 ASCII 快路径，继续优化应合并内部读取状态
  的访问，保留 unread、游标、外部格式和自定义流行为。
- **CST 构造触发通用重建和重新初始化。** reader 的 `make-expression-result`
  会调用 CST 的通用 `reconstruct`；该路径包含约 137 MB 的分配采样权重、
  约 2.0% 的 CPU。它来自 reader 构造 CST，并不是已删除的宏展开后 CST 重建。
  正常列表构造末尾还会 `reinitialize-instance` 设置源码位置，引入初始化协议。
  整轮重新初始化路径约占 5.1% CPU、200 MB 分配权重，后两项含其他调用者。
- **降级反复展开源码位置。** `ir-lower-mv` 和 `ir-lower-branch` 调用
  `ir-source-range`，把打包 fixnum 拆成新 cons；这一叶函数分得约 42.7 MB。
  可以让动态调用位置保持打包表示，只在实际发射调用或调试记录时展开。
- **KIR 的构造与最终表示重复分配。** `new-var`、`copy-to-var`、
  `var-declaration` 的叶权重分别约 97、80、73 MB；`finish-function` 再用
  `mapcar` 构造声明列表。适合尝试让后端直接消费紧凑的变量记录，避免为文本
  表示提前构造列表；这些是各叶的采样归因，并非对象大小清单。
- **哈希访问同时影响前端与降级。** 名字驻留、readtable 的 `syntax-type`、
  `declare-once` 都出现在 `find-place` / `equal-hash-1` 的调用者中。
  外部周期采样两者各约占 2.3%。应先缩小到具体表的键和访问模式，再决定缓存、
  专用索引或替换哈希实现。

外部硬件采样还把 `kirtext::write_form` 定位为约 5.83% 的自身周期，说明内置
分析器把大部分输出时间归到 `check-sys` 只是调用栈归因，不是该 Lisp 检查函数
本身昂贵。内置分析器具有 safepoint 偏差；硬件周期占比、墙钟 tick 占比和
分配权重是三种不同指标，不能相加，也不能直接作为优化后的加速预测。

可重复的单次采样：

```sh
mkdir -p build/compiler-profile-run
cp build/boot/stage0/modules.lisp-expr build/compiler-profile-run/
(cd build/compiler-profile-run &&
 MMTK_GC_TRIGGER=FixedHeapSize:8589934592 KILN_PROFILE=cpu \
 KILN_PROFILE_OUT=cpu.folded ../boot/kiln1 >cpu.log 2>&1)
# 将 cpu 改为 alloc，输出到另一份文件，进行分配采样。
(cd build/compiler-profile-run &&
 MMTK_GC_TRIGGER=FixedHeapSize:8589934592 KILN_FUNCTION_MAP=functions.map \
 perf record -F 499 -g -o perf.data -- ../boot/kiln1)
```

优先顺序是消除顶层分块的重复扫描，再减少源码位置的临时 cons，随后对 reader
的字符读取、CST 构造及初始化协议分别做受控实验。较大的容器和 KIR 表示改动
需要在这些基线上验证时间、分配和内存收益。

### 顶层分块与源码位置优化（2026-11-10）

顶层分块改为单次顺序消费列表，消除剩余列表的重复 `length` 和 `nthcdr` 扫描。
降级的动态调用位置保留打包 fixnum，仅在输出 `:loc` 时提取起止偏移；函数级
调试记录仍按需生成范围。两个版本编译同一份修改后的源码，避免输入规模变化
影响比较。

固定 8 GiB 堆，先分别做一次预热和五次测量，再按旧、新、新、旧的顺序重复
两轮，交替测量各四次。以下为交替运行的中位数：

| 指标 | 优化前 | 优化后 |
|---|---:|---:|
| 整轮墙钟 | 7.271 s | 7.192 s |
| 前端阶段之和 | 3.907 s | 3.918 s |
| 降级阶段之和 | 2.289 s | 2.179 s |
| 输出阶段之和 | 0.598 s | 0.620 s |
| 峰值 RSS | 3,124,048 KiB | 3,087,510 KiB |
| 分配采样总权重 | 3,122,248,600 B | 3,083,881,088 B |
| `ir-source-range` 叶分配权重 | 42,435,176 B | 622,472 B |

降级阶段中位数下降约 4.8%，整轮约 1.1%，RSS 下降约 35.7 MiB。
整轮仍有噪声：独立五次测量的墙钟中位数为 7.168 s 和 7.133 s，约下降 0.5%；
交替运行的单次范围分别为 7.185–7.414 s 和 7.112–7.303 s。因此不能将
整轮 1.1% 当作固定收益。较稳定的变化是减少了约 38 MB 的分配采样权重，
源码位置叶函数的权重大幅下降，且新的 CPU 采样已无顶层分块直接调用
`length` 的路径（旧版此次采样为 147 / 6,886 tick）。

### Reader 的普通列表 CST 构造（2026-11-10）

Eclector 的普通列表路径用表达式与子结果的并行扫描替代 `list-length`、子结果
长度计算和 `every`。扫描受子结果长度约束，因此循环表达式也能退出匹配，继续
进入完整的重建路径。列表根 CST 在构造时直接设置 `:source`，保留尾节点的默认
位置，省去对已构造根节点的 `reinitialize-instance`。

以顶层形式采用顺序分块、源码位置保持打包表示的编译器为基线，比较两种 reader
对同一份源码的编译成本。按旧、新、新、旧的顺序重复两轮，每版四次；固定 8 GiB 堆。此次机器有外部
并行 C++ 编译负载，以下时间只代表该轮竞争环境，不能与此前空闲机约 7 秒的
基线直接比较，也不能视作空闲机器上的固定提速比例。

| 指标 | 原 reader | 优化后 |
|---|---:|---:|
| 整轮墙钟中位数 | 13.270 s | 11.290 s |
| 进程用户态与系统态 CPU 时间中位数 | 13.105 s | 11.190 s |
| 前端阶段之和中位数 | 8.153 s | 6.393 s |
| 峰值 RSS 中位数 | 3,087,020 KiB | 2,881,608 KiB |
| 分配采样总权重 | 3,084,063,120 B | 2,873,312,120 B |
| reader 重新初始化路径的分配权重 | 182,250,872 B | 0 B |

该轮墙钟中位数下降约 14.9%，但旧、新运行范围分别为 12.02–14.48 s 和
10.56–12.49 s，背景负载限制了时间结论。分配采样减少约 201.0 MiB、峰值 RSS
下降约 200.6 MiB；两项都指向更少的初始化和临时对象。旧版 reader 的
重新初始化路径占 CPU 采样 630 / 13,029 tick，新版该路径没有样本；
其他 CLOS 操作仍有重新初始化，不应将整轮该协议的剩余成本也归给 reader。

后续热点仍包括字符流与槽访问器分派、token 与符号查询，以及结构不匹配时的
通用 CST 重建。先在空闲环境复测整轮时间，再针对这些路径分别做实验。

### 字符读取、token 与复杂 CST 重建（2026-11-10）

以普通列表 CST 构造时直接设置源码位置的 reader 为基线，比较三类热点处理：

- 文件流将缓冲、输入起止、输出长度和 UTF-8 缓存集中到原生结构；ASCII 字符
  路径只获取一次状态对象，外层 unread 和游标协议保持不变。
- 每个简单 readtable 的 ASCII 分类使用独立向量，所有语法修改、宏字符安装和
  复制同步更新；token scratch 数组采用可重入的有界池，非局部退出归还，最终
  字符串独立持有，避免客户端保留或嵌套读取时共享可修改存储。
- 编译器 client 的复杂 CST 重建在 car、cdr 间共享只读子 cons 索引，两个分支
  的引用筛选、原子来源选择和构造表仍分别计算。其他 client 的重建协议保持可扩展。

临时统计了自编译中普通列表匹配之外的形状：quote 约 4,941 次、unquote 约
4,869 次、quasiquote 约 1,736 次、function 约 1,149 次、unquote-splicing 约
693 次。它们往往只包裹一个已有子 CST，因此重复建立相同子树索引值得消除；
共享索引保留了原有重建启发式，避免改动歧义原子的位置选择。

固定 8 GiB 堆，两个版本编译同一份修改后的源码，分别预热一次、测量五次；
此轮没有外部并行 C++ 构建。

| 指标 | 基线 | 三类优化后 |
|---|---:|---:|
| 整轮墙钟中位数 | 6.855 s | 6.466 s |
| 墙钟范围 | 6.838–6.966 s | 6.432–6.552 s |
| 各模块前端中位数之和 | 3.555 s | 3.280 s |
| 各模块降级中位数之和 | 2.196 s | 2.146 s |
| 各模块输出中位数之和 | 0.634 s | 0.596 s |
| 峰值 RSS 中位数 | 2,887,868 KiB | 2,830,248 KiB |
| 分配采样总权重 | 2,881,058,960 B | 2,821,413,496 B |
| `read-token` 调用链分配权重 | 297,610,392 B | 259,203,464 B |
| `cons-table` 调用链分配权重 | 11,469,840 B | 6,595,096 B |

整轮中位数下降约 5.7%，前端约 7.8%，峰值 RSS 下降约 56.3 MiB；
分配采样总权重减少约 56.9 MiB。调用链的权重含其子调用，不能相加作为总分配。
一次前后 CPU 采样中，文件 `stream-read-char` 内槽分派的叶权重由整轮约 1.76%
降至 0.06%，`syntax-type` 内 `find-place` 的叶权重由约 0.43% 降到没有样本。
这验证了具体路径变化；采样有 safepoint 偏差，时间收益以未剖析基准为准。

| `&rest`（3 个参数） | 39 | 24 | 1.6× | |

自举时编译器主要在做上表后半部分的事：泛函分派、槽访问、`make-instance`、哈希表、`&rest`、`&key`（见下文自举的 profile）。kiln 编译自己比 SBCL 慢 6 倍左右，原因就在这里。GC 占的约 13%，也主要来自这些地方的分配：`&rest` 列表、浮点装箱、初始化时的 initarg 列表、堆上的 handler。所以只换 GC 解决不了根本问题。

### cl-bench 全量复测与 SXHASH（2026-11-10）

Rust 后端和 runtime 用 release 构建，SBCL 为
2.6.10-1.fc45。运行命令：


字符预算保持不变，比较的是相同取样工作量。

同一天在同一份代码上测 SBCL（跑的是同一个编译器，只是由 SBCL 执行）：旧前端 32.1 秒，IR 前端 **14.2 秒**（kernel 0.4、CLOS 3.9、frontend 0.0、eval 1.4、compiler 8.5）。kiln 的 IR 前端 50.6 秒（kernel 1.5、CLOS 17.9、frontend 0.6、eval 5.0、compiler 25.6），是 SBCL 的 **3.6 倍**；旧前端是 4.0 倍（128.0 / 32.1）。表里“SBCL 编同样的五个模块约 47.5 秒、差距约 2.6 倍”那一行，用的是本轮开始前测的 SBCL 时间：SBCL 执行的也是 kiln 的编译器代码，本轮对编译器算法的改进（一次遍历、少建表等）它同样受益，所以那个倍数偏低，应以这里的同代码对比为准。

之后两项：KIR 文本由运行时直接从列表结构写到文件（`kiln_rt_write_kir`，原来在 Lisp 里逐个字符经流输出，profile 里约 20%），Parcl 的 `map-symbols` 改用哈希表去重（原来是平方级，约 5%）。自举每个阶段 **44 秒**（原来约 51 秒），峰值 RSS 8.8 GB。

再加上 IR 求值器（编译期求值不再经过 Common-boot 的 HIR 求值器）和文件流记住文件偏移之后，机器空闲时完整自举每个阶段 **33.8 秒**（kernel 0.9、CLOS 10.7、frontend 0.5、eval 2.9、compiler 17.7 秒），峰值 RSS 8.7 GB。同一份代码上 SBCL 编五个模块 11.0 秒（kernel 0.2、CLOS 2.3、frontend 0.3、eval 0.7、compiler 7.5），kiln 是它的 **3.0 倍**。本轮开始时 kiln 是 293 秒，快了约 8.7 倍。

再之后，cross-client 的编译期求值从 Common-boot 的 HIR 求值器换成 IR 求值器（[ir.md](../design/ir.md) 的“编译期求值”）。改动前的 profile 里编译期求值约占 15%（HIR 求值器要走 s-expression-syntax、builder 协议、Iconoclast AST、AST-to-HIR 和 thunk 构造），换成 IR 求值器后约 1%。和分支点的 kiln0 背靠背交替各测两次（2026-11-08，load 约 1–3）：**45.3 → 36.2 秒**（−20%；各模块累计：kernel 1.1、CLOS 14.0、frontend 14.6、eval 18.1、compiler 35.0 秒），峰值 RSS 8.8 → 8.7 GB，每个阶段约 36 秒。

之后是统一的特化框架（[specialization.md](../design/specialization.md)：假设、版本格、失效的集中入口，现有的缓存改为经过它）和常量槽名 `slot-value` 的调用点缓存。改动前后的 kiln0 交替各测两次（2026-11-08，load 约 2–3）：自编译一个阶段 **38.4 / 38.2 → 37.9 / 38.2 秒**，不变——框架本身是纯重构，`slot-value` 的缓存只在命中路径加一次 stamp 比较。`bench/compare.lisp` 的 AOT 输出里 `slot-value` **24.7 → 9.9 ns**（同样三次，访问器方法 10.4 ns 不变），`make-instance` 和 `typep` 不变。

再之后是调用点特化（常量类名的构造器对象、已知泛函的调用点缓存、热点构造器和判别函数编成机器码）的第一版。第一版让自编译一个阶段从约 39 秒变成 **58 / 62 秒**（+55%，2026-11-08，与改动前的 kiln0 交替各两次）。profile 里多出来的约 2 万 tick 几乎都在两处：泛函调用点在 CST 遍历这类多态调用点上每次未命中都重填（扫方法的特化参数、扫调用历史、分配描述符），约 20%；构造器反复晋升编译，约 15%，因为描述符检查共享的类型版本，而每个类第一次终结都会改变它，再加上只留 64 项的最近使用表。修正：只比较被特化参数的 stamp；重填达到 8 次的调用点转为 megamorphic；不能缓存的泛函（EQL 特化等）得到直接调用泛函的描述符；守卫改用只在已有类变化时才变的 `*class-change-version*`；类第一次终结不再算变化；构造器对象按类保存不淘汰；晋升阈值 32 → 1000。之后交替各两次：**35.7 / 37.6 → 35.8 / 38.5 秒**，持平。但 `bench/compare.lisp`（AOT，各三次取中位数）上泛函调用反而变慢：单态 13.7 → 28.6 ns，多态 18.9 → 25.7 ns，`call-next-method` 51.9 → 63.2 ns，因为多了选择器那一层调用和三组版本检查；泛函调用点缓存和生成的判别函数因此去掉，改按 PCL 的路线优化判别函数本身（[roadmap.md](../roadmap.md) 第 11 项）。保留的构造器对象：`make-instance`（2 个 initarg，未晋升的闭包路径）437 → 359 ns。移除该缓存后，每个阶段 33.8 秒（load 约 1）。

然后按 PCL 的路线改判别函数：单分派的判别闭包拆成快、慢两个，快闭包只就地取实例的 stamp、探表，命中时尾调用有效方法（KIR 新增 `tail-call-lisp`，即 Cranelift 的 `return_call_indirect`），因此没有普通调用，不保存 callee-saved 寄存器；包装方法快函数的闭包和 funcallable instance 的跳板也改成尾调用；IR 降级的测试位置不再把 `or`、`and`、`not` 里的谓词物化成 T/NIL。`bench/compare.lisp`（AOT，各三次取中位数，与采用普通调用的判别函数相比）：泛函单态 **13.7 → 7.4 ns**，多态 18.9 → 11.9，`call-next-method` 51.9 → 39.4，读取器 10.4 → 5.4，写入器 11.1 → 7.8；流和打印器内部也是泛函调用，`format nil ~a` 8738 → 7531，`read-from-string` 41043 → 32923，`intern` 303 → 227。自编译一个阶段 33.8 → **32.2 / 32.4 秒**。

删掉旧前端（Iconoclast 的降级、`simplify-ast`、Common-boot 和 HIR 求值器，以及只有它们用的 s-expression-syntax、parser.packrat、builder 协议、let-plus、anaphora 等）以后，compiler 模块只剩 Trucler reference、Clostrum、Anatomicl 和 kiln 自己的编译器：完整自举每个阶段 32.4 → **18.4 秒**（2026-11-09），其中编 compiler 模块从约 17.2 秒降到 2.8 秒，其余模块不变。

同一路线继续：按两个参数分派的判别闭包也拆成快、慢两个，带 `&optional` 等的单分派闭包和自动机闭包命中后尾调用；方法体只调用 `call-next-method`、`next-method-p`（没有 `#'call-next-method`）时，它们是局部宏而不是每次分配的闭包。`bench/compare.lisp`（AOT，各三次取中位数）：`call-next-method` **40.6 → 18.5 ns**，单态 7.3、多态 12.0 ns（多态里含 `(mod i 3)` 和 `svref`），读取器 6.2 ns，与之前持平。

然后是函数入口：poll 请求同时把 `stack_limit` 抬到 `isize::MAX`，入口只比较一次帧指针；参数全在寄存器里的函数在读参数之前检查，慢路径尾调用共享的 `kiln_poll_retry`（轮询后再进入原函数），所以命中路径上没有调用，参数不再为 safepoint 存进栈槽。`bench/compare.lisp`（各三次取中位数）：泛函单态 7.3 → **6.9 ns**，`call-next-method` 18.5 → 17.8，`fib 20` 约 58.5 → **51.4 µs**，`format nil ~a` 7.9 → 7.4 µs，`read-from-string` 33.3 → 32.4 µs。自编译一个阶段 18.7 秒（持平）。

接着修掉 `underlying-file-stream` 的包名错误（`files.lisp` 在 `cyclosis` 包里，而 `cyclosis:synonym-stream-symbol` 遮蔽了 `cl:synonym-stream-symbol` 并期待 `client` 参数，导致 `with-open-file` 传入的文件流未命中 `kiln_rt_write_kir` 快路径，回退到 Lisp 逐字符输出 KIR），并做几项前端和宏展开消分配：
- `multiple-value-bind` 的展开直接归约为多值 `let` 节点，按返回值个数从 `v0` 和 `ctx.values` 取值，不再生成续延闭包、把被赋值外层变量放进堆单元、或把外层 `return-from`/`go` 变成非局部退出；`(multiple-value-call #'list ...)`（`multiple-value-list`）直接返回 `nreverse` 列表，不再经 `apply` 拆回再建表；常量小下标 `nth-value` 展开成 `values` 或 `multiple-value-bind`。
- `check-type` 的 `store-value` restart 移进 `check-type-error`，命中路径不再建闭包、变量单元和退出令牌（原来 `read-char` 和 `peek-char` 每次调用都分配它们，占自举分配量的 10%）；`handler-case` 空参数列表的子句不再给外层条件变量赋值。
- 编译器里频繁调用的 `ir-parts`、内联参数校验和复合 `typep` 检查用无分配的 `ir-proper-list-p` 代替 `(handler-case (list-length ...) (type-error () nil))`；没有 `optimize` 声明的函数复用外层的 `optimize-description`；`emit` 用 `case` 判断终结指令（原来每次调用读 `*terminators*` 并调 `member`），`bname` 声明为内联。
- 结果：自编译一个阶段从 18.7 秒降到 **7.0–7.2 秒**（Lisp 时间 **6.5 秒**：kernel 0.3、CLOS 3.7、frontend 0.1、eval 1.2、compiler 1.2 秒），整个阶段分配总量从超过 8 GB 降到 **3,454 MiB**，在 8 GiB 自举堆下 **0 次 GC**，峰值 RSS 从 8.7 GB 降到 **3.5 GB**。同一份代码上 SBCL 编五个模块 **4.63 秒**（kernel 0.27、CLOS 2.80、frontend 0.10、eval 0.61、compiler 0.85 秒），kiln 是 SBCL 的 **1.4 倍**。`bench/compare.lisp`（AOT，三次取中位数）：`read-from-string` 32.4 → **20.3 µs**，`format nil ~a` 7.4 → **5.6 µs**，`intern` 227 → **112 ns**，`gethash equal` 85 → **50 ns**，`(setf gethash) eq` ~60 → **17.8 ns**，`handler-case` 73 → **39.9 ns**，`make-instance` 359 → **305 ns**。

再做一轮针对自编译剩余热点和 CLOS 分派的优化（2026-11-09）：
- **去掉顶层宏展开的 `cst:reconstruct`，按需惰性构建 `*ir-form-sources*`**：`cst:reconstruct` 是旧 Iconoclast 前端留下的（每个宏展开新建 5 张哈希表、工作表和大量 `cst` CLOS 实例，占自编译分配量的约 500 MB）；现在 `process-toplevel` 直接处理宏展开出的普通形式，`*ir-form-sources*` 只在 `ir-input-source` 真正遇到宏展开传下来的普通 cons 时才按顶层 CST 建一次。
- **`defmethod` 单次编译与直接返回快函数、预计算 `call-next-method`、融合槽写入器**：原来 `method-lambda-forms` 把方法体同时塞进慢函数和快函数编译两遍；现在只编一个函数，慢槽由 `method-function-from-fast` 包装得到（`clos.kir` 从 76 MB 降到 63 MB）。不引用 `call-next-method`/`next-method-p` 的快函数（95% 以上的方法）直接以 `(lambda (a0 ... a_{n-1}) ...)` 作为方法函数，去掉 `next-methods` 首参（3 参数方法也能走提前 poll），`spread-method-call` 直接返回它而不包一层闭包；只做零参数 `(call-next-method)` 的快函数在构造有效方法时就绑定好下一个方法的展开调用函数，调用时不再读方法槽；单分派判别闭包把槽写入器也像读取器一样融进缓存，命中时就地写槽；`mentions-p` 等扫描函数延迟分配循环检测哈希表。
- **字符比较与 `/=` 原语、序列函数直接遍历**：`char=`、`char/=`、`char<`、`char>`、`char<=`、`char>=` 和 `/=` 作为编译器原语内联（省掉自举中 `char=` 的 129 MB `&rest` 列表分配）；`find`、`position`、`count`、`remove`、`every`、`some`、单序列 `map` 直接在列表和向量上循环，不再先用 `seq-list` 复制成列表。
- 结果：自编译一个阶段墙钟从 7.0–7.2 秒降到 **5.4 秒**（Lisp 时间 **6.5 → 5.0 秒**：kernel 0.2、CLOS 3.0、frontend 0.1、eval 0.8、compiler 0.9 秒），分配总量从 3,454 MiB 降到 **2,581 MiB**（0 次 GC），峰值 RSS 从 3.5 GB 降到 **2.5 GB**，已接近同一份代码上 SBCL 的 **4.63 秒**（差距约 **8%**）。`bench/compare.lisp`（AOT）：泛函单态 6.9 → **6.3 ns**，多态（3 类）11.9 → **9.3 ns**，`call-next-method` 17.8 → **9.6 ns**（和 SBCL 的 9 ns 持平），写入器 7.1 → **6.8 ns**，`find` 字符串 1812 → **596 ns**，`read-from-string` 20.3 → **17.3 µs**。

845 秒那次的 profile（按模块统计自身时间）：

| 部分 | 占比 |
|---|---|
| clos 模块（分派、slot 访问、实例初始化、哈希表） | 约 45% |
| kernel 模块（`member`、`typep`、`logand` 等） | 约 27% |
| GC（MMTk 工作线程） | 约 17% |
| compiler 模块自己的代码 | 约 3% |
| Maclina 的字节码 VM | 约 1%（包含时间 14%，几乎都是它调用的原生函数：parser.packrat 的规则） |

所以换成原生 `compile` 几乎不会让自举变快：字节码只是一层很薄的胶水。HIR 求值器的参数解析器改用原生编译后，一个阶段反而从 321 秒变成 357 秒（每个只运行几次，编译时间占主导）。

321 秒之后剩下的热点（CLOS 阶段）：GC 约 13%；kernel 的函数约 21%，比较分散；Salmagundi 哈希表约 5%；`append` 方法组合（Iconoclast 的 `slot-designators`，walker 每访问一个节点调用一次）约 5%；`&rest` 泛函每次调用分配参数列表。

其他观察：
- 试过 Immix（`MMTK_PLAN=Immix`）：比 SemiSpace 慢约 5%。
- MMTk 的 debug assertions 检查每次 side metadata 访问，GC 曾占约三分之一的时间，dev 构建里对 mmtk 关掉了。
- compiler 模块在 2 GiB 堆（SemiSpace，可用一半）下跑了 51 分钟后内存不足：存活数据接近半堆时几乎一直在 GC。
- kiln0：`kiln-cg` 编六个 KIR 约 15 秒，峰值内存约 9.5 GB；可执行文件约 120 MB；启动（各模块的顶层初始化）约 0.65 秒。stage1 峰值 RSS 约 9 GB（8 GiB 堆）。
- kiln 上编 `co-compile`（约 100 行）：最初 AOT 程序连启动 12 秒（SBCL 不到 1 秒），修掉自动机重建等之后 2.3 秒。

## GC

kiln0 编译五个模块（一个自举阶段），SemiSpace，固定 8 GiB 堆（每个半区 4 GiB），GC 线程 8 个，debug 构建的 runtime（MMTk 是 opt-level 2、关掉 debug assertions），`KILN_GC_STATS`（[gc.md](../design/gc.md)）。测量时机器上还有别的任务在跑（load 4–18），同一个程序的墙钟时间在 380–460 秒之间波动，所以下面只比较 GC 自己的量；单次运行里 mutator 时间的差别看不出 3% 以下的变化。

### 基本数字

| 量 | 值 |
|---|---|
| 回收次数 | 66 |
| 分配总量 | 约 250 GB（255 560 MiB），约 600 MB/s |
| 每次回收后的存活量 | 平均 490 MiB，最多 1.24 GiB；kernel 和 CLOS 阶段 30–700 MiB，编译 compiler 模块时从 100 MiB 涨到 1.2 GiB |
| 复制总量 | 32 GB，分配量的 12.7% |
| 停顿 | 合计 31–39 秒（三次运行；墙钟的 8.5–9%），平均 0.46–0.59 秒，最长 2.2–2.8 秒 |
| GC worker 的 CPU | 89–109 秒，整个进程 CPU 的 21–23%（perf 的采样也是 21.5%） |
| static root | 108 401 个 |
| 峰值 RSS | 约 10 GB |

停顿和存活量成正比，约 1.1 秒每 GB：存活 100 MiB 时 0.19 秒，500 MiB 时约 0.9 秒，1.2 GiB 时 1.6 秒，个别回收到 3 秒。

### 复制的几乎全是老对象

`KILN_GC_AGES=1` 把每次复制的字节分成“上次回收之后分配的”（young，nursery GC 要复制的）和“上次回收复制过的”（old，分代 plan 不再复制的）：

| 运行 | 回收间隔 | 回收次数 | young | old |
|---|---|---|---|---|
| 五个模块 | 约 4 GiB | 66 | 2.2 GB | 28.5 GB（93%） |
| kernel 加 CLOS | 约 4 GiB | 18 | 809 MiB | 4.1 GB |
| kernel 加 CLOS，每分配 256 MiB 回收一次（`MMTK_STRESS_FACTOR`） | 256 MiB | 282 | 842 MiB | 72.8 GB |

新分配的对象只有约 1.1% 活过下一次回收，而且回收间隔从 4 GiB 缩到 256 MiB 时这个比例几乎不变（809 → 842 MiB）：编译器的临时对象寿命远短于 256 MiB 的分配量。所以 256 MiB 的 nursery 在整个自举里大约复制 2.5 GB（每次约 3 MB），而 SemiSpace 复制了 32 GB。

**分代的估计**：nursery GC 按现在的复制速度约 1.1 秒每 GB，晋升约 2.5 GB 合计约 3 秒；每次 nursery GC 还要扫描栈和 10 万个 static root，约 1000 次合计 1–2 秒；mature 空间涨到 1.2 GiB，8 GiB 堆里只需要几次 full GC，每次约 1–1.5 秒。合计 6–9 秒，现在是 31–39 秒，墙钟省约 25–30 秒（7% 左右），GC worker 的 CPU 省约 80 秒。写屏障要还回去 mutator 的 1–3%（4–11 秒）。净收益约为墙钟的 4–6%，GenImmix 还能把同样的堆的可用空间翻倍、RSS 降下来。设计见 [gc.md](../design/gc.md) 的“Generational GC plan”。

### GC 的并行度

| GC 线程 | 停顿 | worker CPU |
|---|---|---|
| 4 | 36.8 秒 | 93 秒 |
| 8（默认） | 31–39 秒 | 89–109 秒 |
| 16 | 35.5 秒 | 118 秒 |

线程数几乎不影响停顿：8 个线程时平均只有约 3 个在干活。按 20 毫秒分段统计 perf 样本里同时出现的 worker 数：只有 1 个 worker 的段 739 个，2 个 540，3 个 305，4–7 个合计 69，8 个全忙 531。只有一个 worker 的时段里，热点和全忙时一样（`trace_object`、side metadata、复制），不是调度开销，而是可做的工作窄：链表这种只能顺着一条指针链走的结构。试过：
- root 分包（static root 原来一个包十万个槽）：停顿不变（33.9 秒），说明瓶颈不在 root。保留了这个改动，它本身没有坏处。
- 把 MMTk worker 的本地缓存包数从 16 改成 1（强制把新包放进全局队列，唤醒空闲 worker）：停顿翻倍。不过所有改过 MMTk 源码的构建（用 `[patch]` 指向 MMTk 的副本）停顿都约 59 秒，连只改清零的那个也是，所以这个对比不可信，原因没查。

结论：GC 线程数没有可调的收益，4 个线程省约 10% 的 GC CPU、停顿略长。默认值不变。

### GC 时间花在哪里（perf，worker 的样本）

side metadata 的地址计算和读写（forwarding bits）约占 worker 时间的 25%，`trace_object` 14%，`copy` 7%，写 forwarding 指针时 MMTk 用 CAS 循环更新整个 header 字（`fetch_update`）约 7%，bump 分配约 5%，`object_bytes` 3%。forwarding bits 放在 side metadata 是因为 header 的低字节是 kind；如果像 roadmap 里无 header cons 的方案那样给 header 的低 3 位留出保留 tag，forwarding bits 就能放进 header，省掉这部分的大半。

### 清零

- MMTk 的空间取得新页时清零（kiln 用到的 plan 都写死了 `zeroed = true`），这是 mutator 线程上的 `memset`：约 1.9% 的样本（250 GB 的分配全部清零一遍），GC worker 上还有 0.6%（GC 复制的目标块也先清零，完全白做）。
- `kiln_rt_alloc` 原来在 MMTk 已经清零的内存上再清零一遍（不经内联快路径的分配：变长向量、大于 128 字节的对象）。去掉了；它在 perf 里只占 0.1% 左右，墙钟上量不出来。编译出的代码的内联快路径也逐字写零，同样多余（`lisp/lower.lisp` 的 `emit-alloc`），可以去掉。
- 反过来做（MMTk 不清零、只靠 kiln 自己清零）要改 MMTk 的 SemiSpace，收益估计是 CPU 的 2.5%、mutator 时间的约 2.4%。不值得为此维护 MMTk 的分支；换分代 plan 时 nursery 同样写死清零，到时候再看。

### 堆大小和触发策略

| 堆 | 回收次数 | 停顿 | worker CPU | 峰值 RSS |
|---|---|---|---|---|
| 固定 8 GiB | 66 | 31–39 秒 | 89–109 秒 | 9.9 GB |
| 固定 12 GiB | 42 | 25.4 秒 | 71 秒 | 14.8 GB |

SemiSpace 的 GC 时间约等于“回收次数 × 平均存活量”，堆加大一半，回收少三分之一，停顿省约 10 秒（墙钟 2.5%），代价是多 5 GB 内存。自举的默认堆（`KILN_BOOT_HEAP`）不变：分代 plan 会让堆大小不再重要。

### release 构建的 runtime

紧挨着跑的两次（load 约 2–3）：debug runtime 停顿 30.6 秒、worker CPU 89 秒、墙钟 344 秒；release runtime（`cargo build --release`，像 `tools/bench.sh` 那样链接）停顿 30.5 秒、worker CPU 88 秒、墙钟 333 秒。GC 的数字一样：dev 构建里 MMTk 和 kiln-rt 本来就是 opt-level 2，MMTk 的 debug assertions 也关了。墙钟差的 11 秒在 mutator 一侧（runtime 函数、debug assertions），在这台机器的噪声范围内。

## 字节码 VM（Maclina）

`(fib 25)` 在 REPL 里由字节码执行（AOT 可执行文件），SBCL 的编译代码约 1 毫秒：

| 改动 | 秒 |
|---|---|
| eval 模块刚完成时 | 5.70 |
| 字节码存成 simple vector（原来是 Regalia 的 `(unsigned-byte 8)` 数组，`aref` 要经过几层泛函和 `typep`） | 1.90 |
| 结构的访问器不再是泛函 | 1.27 |
| `ash` 的 fixnum 快速路径 | 1.18 |
| `ceiling`、`round` 的 fixnum 快速路径（`(loop repeat n)` 用到 `ceiling`） | 0.81 |

| `(eql x 常量)` 按 `eq` 降级；一个下标的 `aref` 就地读写 | 0.55 |

剩下的开销：主循环本身约占三分之一，热点是循环头的一长串栈槽到栈槽的搬移：大约二十个值活过整个循环，主要是 VM 的局部函数（`spush`、`spop` 等）的闭包对象，它们都被 spill 了。对不逃逸的局部函数做 lambda lifting 或内联小的局部函数能解决，这对所有代码都有用。

## I/O

接入流和 FORMAT 时：往字符串流或文件写一个字符要 1 ms 左右，`format` 一次 10 ms。泛函调用本身约 0.5 µs，慢在字符串输出流平方级的增长、可调数组的增长走完整的 `make-array`、每个字符都调用的 `check-character-stream` 里的 `subtypep`、Invistra 每次重新解析控制串。修掉之后往文件写一个字符约 30 µs，`format` 一次 0.3–0.7 ms，`princ-to-string` 约 0.4 ms。上面对比表里的 `format` 是这之后的数字。
