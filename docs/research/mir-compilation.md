# HIR 分析迁移到 MIR 的编译性能测量

日期：2026-11-16。

MIR 迁移同时增加了 Lisp 端的分析成本和后端处理成本。回退并非主要来自
Cranelift 的机器码优化：六个模块的完整后端耗时从 21.42 s 增至 44.67 s，
其中 Cranelift 机器码生成只从 1.43 s 增至 2.97 s。更多的 LIR、控制流和
poll 慢路径还增加了 LIR 降级、调试信息和目标文件生成的工作。

针对重复分析、类型检查、poll 和浮点临时值的优化降低了成本，但仍未恢复
HIR 的吞吐量。相同 kernel 输入由原生编译器编译时，模块前端、降级和输出
合计从优化前的 24.76 s 降至 15.38 s，历史 HIR 为 2.03 s。

## 测量范围和方法

机器为 AMD Ryzen 9 7940HS，8 核 16 线程，开启 boost；SBCL 为
2.6.10-1.fc45，Cargo.lock 中 Cranelift 为 0.137.1。所有测量串行进行。
历史 HIR 使用保留双流水线的版本 `2789342`，优化前 MIR 使用 `f871ae4`。
优化后为本文所述的 MIR 分析和降级规则。旧版本的 eval 模块还包含旧 HIR
编译器实现，因此其模块规模并非严格相同的源码工作负载。同一 `2789342`
版本另用 MIR 编译作控制：CLOS 降级 8.83 s，eval 降级 27.77 s；对照同版
HIR 的 1.10 s 和 1.23 s，确认新增流水线本身已造成回退。

SBCL 的阶段时间来自各一次带 CPU 采样的 stage0 编译，用于定位热点，
不是稳定性能预算。阶段边界分别是 `front-end`、`compile-module` 和
`write-module`；模块合计不包括加载依赖和 stage0 初始化。SBCL 空间上限
为 8 GiB。采样中块参数计划约占 18–23%、函数身份分析约占 13–14%、
验证器约占 20% 的包含调用时间；这些调用栈重叠，比例不能相加。

后端对保存的各模块 LIR 使用同一 release 构建的 `kiln-cg obj`，默认代码
生成优化级别。预热一次后测三次，分别取各模块中位数。完整后端时间包括
进程启动、解码、LIR 降级、调试信息和目标文件输出；Cranelift 时间取
`KILN_TIME=1` 输出的 `machine code in`。合计是各模块中位数之和。
LIR 大小按二进制包文件字节数计，MiB 为 2²⁰ 字节。

## 热点与优化边界

类型谓词折叠原先在每个函数改写后使整个 unit 的调用摘要和类型分析失效。
一个 unit 有许多可折叠函数时，同一批信息会反复计算。现在先从一个分析
快照收集本轮所有改写，再统一应用，下一轮才重算摘要，直到固定点。
改写保留程序行为，因此本轮已证明的折叠仍然有效。

SSA 简化中的转发链会被许多使用点重复追踪。现在查询时压缩路径，并在
没有受保护的细化参数时跳过第二轮别名处理。内部调用验证只在存在间接
调用或多值调用时计算函数身份流；直接调用继续使用原有检查。
HIR 缓冲区和 MIR 的整数元数据补充槽类型，使 SBCL 能减少通用数值和
数组操作。目标端结构访问器尚未传递槽的结果类型，因此这部分收益不能
直接推算到原生编译器。

向量访问已有 simple-vector、fixnum 索引和非负区间证明时，降级不再
重复测试对象类别、整数类别或负数条件；长度上界仍逐次检查，无法证明的
条件仍保留。函数入口和循环仍需要处理 GC、抢占和栈检查，但无环的内部
基本块不需要额外 poll。现在用 CFG 的循环强连通分量选择 poll 点，覆盖
自环和多入口循环，原语内部循环保留自己的 poll。

高 debug 策略原先阻止所有 double-float SSA 值使用原始浮点局部量。
现在无源码观察点的算术中间值可以保持 f64；命名绑定、参数和合流值仍
保留对象存活关系。两步未命名浮点运算只在最终返回时分配一个对象，
源码观察得到的中间结果仍分配独立对象。这个边界保留调试帧中的值和对象
身份，也避免仅为后续算术操作装箱。

## 原生编译器吞吐量

为区分宿主 SBCL 与 kiln 自身的执行效率，三个完整模块程序使用相同
Rust launcher/runtime 和代码生成配置链接，编译同一份 kernel 清单。
MMTk 堆为 8 GiB，预热一次、测三次。进程总时间还包括 image 初始化等
固定成本；模块时间是程序输出的阶段中位数之和。

| 指标 | 历史 HIR | MIR 优化前 | MIR 优化后 |
|---|---:|---:|---:|
| 进程总时间（s） | 5.17 | 36.26 | 23.63 |
| 前端（s） | 0.46 | 2.75 | 1.89 |
| 降级（s） | 0.30 | 15.53 | 9.12 |
| 输出（s） | 1.27 | 6.48 | 4.36 |
| 模块合计（s） | 2.03 | 24.76 | 15.38 |
| 峰值 RSS（MiB） | 3077 | 8512 | 8468 |

优化后的模块耗时减少约 38%，但前端和输出也仍慢于历史 HIR，说明剩余
差距不只来自 MIR 增加的分析步骤。后续需要对原生编译器取样，区分
高 debug 下可变绑定的堆单元、未传播的结构槽类型和图分析本身的成本。
这些是待验证方向，不能由上述阶段时间分配各自占比。

## 共享 base 的测试预算

共享 base 的测量将冷构建和热测试分开。冷构建强制重建 base，但保留
Cargo 和 SBCL FASL 缓存；热样本必须命中同一个 base。工作负载包括浮点
局部量、向量检查、调试帧、数组调用、多值调用和死块六个测试，每个测试
包含编译、普通加载和 64 MiB 堆的压力加载。默认普通堆为 1 GiB。

[维护的基线](../../bench/baselines/shared-base.json) 固定测试顺序、源码
哈希、运行条件和三次热样本的中位数。其冷 base 构建为 89.34 s，快照
为 5.98 s，热测试为 10.11 s。base 与所选测试产物的逻辑大小为
342.51 MiB，实际分配为 342.59 MiB，其中 base 为 341.44 MiB。
磁盘统计去重硬链接、跳过符号链接，同时报告逻辑与实际分配字节；旧的
无关测试产物不进入所选工作负载预算，所选测试生成的目录和 image 会计入。

在相同六项工作负载下，采用分析与索引检查优化后、进一步减少 poll 和
浮点装箱前，热测试为 12.14 s、所选产物为 360.45 MiB；上述规则使其
分别减少约 17% 和 5%。这是该阶段的对照，不是迁移前 HIR 的测试基线。

复测并比较预算：

```sh
python3 tools/bench-tests.py --baseline bench/baselines/shared-base.json \
  --output build/bench-tests
```

默认容许 10% 回退，超出时间或磁盘预算返回非零；`--rebuild-base` 同时
比较冷构建和快照时间。更换机器、测试源码、顺序或堆配置时，应重新建立
可比基线。base 缓存只依赖实际构建输入，修改测量驱动本身不会触发全量
重建。

后端可以独立复测，避免将 Lisp 编译和 Cranelift 时间混在一起：

```sh
python3 tools/bench-compiler.py --lir-directory build/boot/stage0 \
  --backend target/release/kiln-cg --runs 3 --warmup 1 \
  --output build/bench-codegen
```

目录需包含要比较的模块 `.lir`；历史流水线需使用对应版本生成输入。
原生模块测量的清单和阶段计时用法见
[编译性能设计](../design/compiler-performance.md)。
