# 编辑器和 IDE（暂名 KilnWorks）

设计草案，还没有开始实现。这里定下架构原则和对 kiln 运行时的需求，具体接口等开工时再写。Lisp 以纯函数的形式进入显示管线，平台层和 GPU 渲染在 Rust（[rust-interop.md](rust-interop.md)）。分阶段计划见 [roadmap.md](../roadmap.md) 的“编辑器”。

## 定位

KilnWorks 是用 kiln 写的编辑器，同时是 kiln 自己的 IDE。它有两个作用：
- **kiln 的驱动应用**：依赖追踪、按上下文局部的变量、fiber、debugger、部分 seal、体积这些运行时功能，都要有一个真实的用户来确定需求和优先级。
- **Emacs 式的可扩展性**：既能修改编辑器本身（命令、按键、钩子、选项），也能在编辑器上构建完整的应用（REPL、inspector、debugger、版本控制界面、文件管理）。

非目标：
- 不兼容 Emacs Lisp，也不复刻 Emacs 的 API。只借鉴它的架构决定。
- 先做 TUI。GUI 的分层已经定下（“显示”），前端的平台层和渲染器用 Rust 写，经 [rust-interop.md](rust-interop.md) 的宿主模块接入，不必等 seal。

## 可扩展性从哪里来

分析 Emacs 可以看到，它的可扩展性有三个来源：
1. **架构决定扩展点在哪里**：命令循环在哪里交出控制权，按键查找有哪几层，输入框是不是 buffer，核心的状态是不是扩展代码能直接读写的变量，各个子系统的入口有没有分派点。
2. **运行时让扩展点变得廉价**：符号间接调用、即时重定义、动态绑定。加一个扩展点只需要读一个变量或者通过符号调用一个函数，不用设计 API。
3. **积累决定扩展点有多少、有多细**：可替换的大小写表、字符宽度表、按位置覆盖的语法、可以携带回调的 undo 记录。每一项都是某个时候为某个需求做的决定。

换一门更强的语言，只能加强第 2 项。用 CL 写的编辑器并不会自动比 Emacs 更可扩展：如果缺了第 1 项，CL 的能力就找不到地方发挥。所以本文大部分篇幅都在讲架构（“细腰”、“核心架构”），运行时的需求单列一节（“对 kiln 运行时的需求”）。第 3 项只能靠时间积累，但可以从一开始就采用会产生积累的手法（“会产生积累的手法”）。

还有一个反面的结论：**语义往往定义在某条架构边界上**。照搬某个行为之前，先问它依附在哪条边上，那条边在这里有没有。没有的话，先把边补出来。否则只能用分散的字段和判断去模拟，组合起来就会在没想到的路径上出错。命令循环（“命令循环：显式的边界”）是最典型的例子。

## 细腰

编辑器的各个组件共同依赖的那一层叫“细腰”。可选的细腰按表达力从弱到强排：纯文本、加了颜色和光标控制的终端字符、**buffer 加带属性的文本**、HTML/canvas。KilnWorks 选第三种，和 Emacs 一样：
- 比终端字符更通用，也更有原则；
- 比 HTML/canvas 弱，但保住了文本的可组合性：界面的状态就是文本，所有文本工具（搜索、替换、多光标、键盘宏）都能直接用在任何界面上。例如在可编辑的目录列表里用查找替换批量改文件名，不需要专门的批量重命名功能。

**只有一种东西**：输入提示、候选列表、帮助、REPL、编译输出、debugger 的回溯，都是 buffer。这条决定的好处是“白得”的能力：输入框里自动有全部编辑命令，因为它本来就是 buffer。

**属性词汇表要封闭到什么程度，是细腰真正的粗细所在。** “带属性的文本”概念上很简单，但每多一种带行为的属性，尤其是会在显示时回调 Lisp 的属性，细腰就粗一点。到最后，要准确复刻显示，就得复刻整个运行时。

Emacs 的重显示会在许多地方执行 elisp：`fontification-functions`（jit-lock）、mode line 的 `:eval`、`display` 属性的条件、`pre-redisplay-function`、`window-scroll-functions`。问题不在于执行 Lisp，而在于执行的方式：
- 执行的代码能修改 buffer、窗口和变量，C 端只好到处加 `inhibit-*` 标志防止重入和半途的状态；
- 代码同步运行，慢了画面就停住，出了错只能吞掉（“Error during redisplay”）；
- 显示过程和编辑状态缠在一起，没法把渲染挪到另一个线程。

但 jit-lock 背后的思想是对的：只为看得见的部分按需计算。KilnWorks 的决定：
- **显示用的属性都是声明式的数据**：face、不可见、替换显示、对齐空白、图片。`display` 属性里不能写要求值的条件。
- **重显示中可以执行 Lisp，但只能是作用于不可变快照的纯函数**：结果是数据，有缓存，有时限，出错按函数隔离。可扩展的计算以装饰提供者和布局函数的形式进入显示管线（“显示”），而不是插在显示过程中的钩子。要修改状态的钩子在取快照之前运行。
- **行为属性**（只读、field、按键表、修改钩子、光标进出钩子）在编辑操作中触发，不在显示时触发。

这样显示管线的每一段只依赖上一段的数据，可以整体快照，可以把渲染交给另一个线程或进程。TUI 和 GUI 共用前面几段，只在最后一段分开。代价是放弃“显示时修改任意状态”这种最深的扩展能力，这是有意的取舍。

## 核心架构

### buffer 和文本

- **文本**：数据结构（gap buffer、rope 或 piece table）待定（见“待定问题”）。对外只暴露按字符位置的接口。
- **文本属性**：区间树，挂在 buffer 和字符串上，插入、复制时随文本移动。前后粘性决定插入的文字是否继承属性。
- **marker 和 overlay**：随编辑移动的位置和区间。两端在插入时是否推进，分别可设。
- **narrowing**：把 buffer 限定在一个区间内，所有原语都只看得见这个区间。只作用于子树的命令因此不需要知道文档结构。
- **indirect buffer**：和基础 buffer 共享文本和属性，有自己的模式、narrowing、overlay。可以用它以另一种语言的模式编辑嵌入的代码块。
- **每个窗口有自己的 point**。

### 命令循环：显式的边界

一次按键序列解析成一条**命令**，命令有明确的开始和结束。下面这些都挂在这两条边上，而不是各自用一个字段模拟：
- `this-command`、`last-command`、当前命令的按键序列；
- 前缀参数（`C-u` 之类）：属于下一条命令，不单独成为命令；
- 命令前后的钩子；
- 键盘宏的边界：只在命令结束、且没有待用的前缀参数时确认；结束录制的命令连同它的前缀参数都不进宏；
- 只对下一条命令生效的临时按键表；
- undo 边界。

定时器、异步任务的回调、扩展代码直接调用的命令，都**不经过**命令循环，因此不触发命令前后的钩子、不进键盘宏。这和 Emacs 里定时器在命令循环之外运行一致。

**执行命令本身是一个可重定义的函数**：命令循环通过符号调用它，“执行一条命令意味着什么”由 Lisp 定义，可以被替换或 advice。

**可重入**：等待输入（输入提示、确认、递归编辑）就是再跑一层命令循环。在 kiln 上用 fiber 实现：读输入的函数写成同步调用，实际是挂起当前 fiber 等待输入事件（“fiber”）。

### 按键

- **按键表是数据**：可以构造、继承、遍历，没有不透明的对象。
- **分层查找，顺序固定**，从高到低大致是：覆盖表 → 光标处文本的按键表属性 → 模拟层（模态编辑插件挂在这里）→ 次模式 → buffer 局部（或光标处文本的局部表）→ 全局。每一层都是一个变量或一个文本属性。模态编辑因此可以作为插件存在，按钮、链接、diff 片段也都能有自己的按键。
- **按命令重绑定**：按键表里可以写“凡是绑定到命令 A 的键，在这里改成执行 B”，模式替换的是语义上的操作，而不必猜用户把它绑在哪个键上。
- **可编程的输入解码**：终端的转义序列怎么解码成按键、按键怎么翻译，都是可以修改的数据。新终端、新的键盘协议不必等编辑器发版本。
- **事件队列可写**：程序可以往输入队列里塞事件，键盘宏回放用的是同一套机制。

### 焦点和输入框

焦点就是当前选中的窗口，没有第二套焦点状态。输入框的实现：
1. 一个普通 buffer 放进输入框窗口；
2. 选中这个窗口；
3. 提示文字作为普通文本插入，带上 field 和只读属性，光标移动和删除都由通用的 field 机制约束，不越过提示；
4. 再跑一层命令循环（“命令循环：显式的边界”）。

所以输入框里可以用全部编辑命令，可以搜索、粘贴，可以嵌套打开另一个输入框，这些都不需要专门实现。这条依赖三个前提：窗口和 buffer 统一、命令循环可重入、文本属性足够通用。三者缺一不可：**输入框是整个架构的产物**，不是一个功能。如果提示和 buffer 是两种东西，就会有两套输入路径和焦点状态，必须互相同步，很难做干净。

### 显示

重显示是一条管线，每一段的边界都是数据：

```
编辑状态 ──(1)──> 快照 ──(2)──> 装饰后的视图 ──(3)──> 帧 ──(4)──> 像素或终端
          重显示前钩子      装饰提供者          布局           渲染
          （可改状态）      （纯函数，按区域，   （纯函数，      （Rust 或
                             缓存，时限）         Lisp）          终端前端）
```

#### 重显示前钩子

在编辑线程上、取快照之前运行，**可以修改状态**：视口跟随、滚动时要调整的东西（Emacs 的 `pre-redisplay-function`、`window-scroll-functions` 里那些确实要改状态的用法）。它们结束后取快照。快照的代价要是常数级，所以文本要用持久化的结构（“待定问题”）。

#### 装饰提供者

对应 jit-lock，也就是 Neovim 的 decoration provider 那种受约束的形式：
- 提供者是按 buffer 或模式登记的 Lisp 函数，输入是快照和一个区域，输出是数据：face、虚拟文本、inlay、行尾注记、行号栏的标记。
- 它只拿到只读快照，**改不了编辑状态**，也就不存在重入。
- 结果按“buffer 版本加区域”缓存。编辑之后只让受影响区域的缓存失效；提供者读过的变量和区域记为依赖，是 [dependencies.md](dependencies.md) 依赖追踪在运行期数据上的推广。
- **有时限**：在时限内完成就同步用；超时就先用旧的或空的结果显示，计算转成异步任务，完成后再重显示。慢的提供者只会让高亮晚到，不会让画面停住。
- **错误按提供者隔离**：出错的区域用不加装饰的样子显示，错误记下来，反复出错的提供者自动停用。阶段边界上的 handler 提供“跳过这个区域”“停用这个提供者”的 restart；开发期可以进 debugger 查看出错的那次调用，画面不受影响，因为上一帧已经画出来了。
- mode line、header line、边栏也是提供者：纯函数，输出带样式的文本，按读过的输入缓存。

#### 布局

布局也用 Lisp 写，是“装饰后的视图、窗口尺寸、量宽服务 → 帧”的纯函数：
- kiln 是原生编译的，布局用 Lisp 写也够快。Emacs 只能把布局写在 C 里。布局因此可以扩展：折行规则、折叠、虚拟行、对齐。
- **量宽服务**由前端提供，带缓存，可以同步调用：GUI 给出整形后的像素宽度，终端给出列数。布局对它泛化，同一份布局代码服务两种前端。
- **字符宽度**（终端）用一张可以修改的覆盖表，默认值来自 Unicode。东亚歧义宽度字符和 emoji 在不同字体、终端下的宽度不一致，用户可以自己调整。
- 布局是纯函数，命令可以直接调用它回答“下一可视行在哪里”“鼠标点在哪个位置”，不依赖上一次重显示留下的状态（Emacs 的 `posn-at-point` 要求先重显示）。
- 平滑滚动时，布局在视口外多排一段余量，滚动只移动图层的偏移（“渲染和 GUI”）。

#### 渲染和 GUI

帧是**显示列表**：
- **图层**：每个窗口的正文、浮层、光标各是一个图层，带位置、裁剪和滚动偏移。Lisp 只更新变了的图层，渲染器保留其余的。
- **图元**：定好位置的字形串、圆角矩形、描边、波浪线、图片，各带裁剪区域。扩展性在这一层：自定义装饰、行内控件、面板、图表都是往显示列表里加图元。
- **资源用句柄**：字体、图片、字形图集由前端持有，显示列表里只放句柄。
- **编码**：字节缓冲区。进程内直接借给前端（[rust-interop.md](rust-interop.md) 的“GC 安全：用借用检查器静态保证”）；同一格式以后也可以经后端协议送到另一个进程或远程。

GUI 前端分四层，“画什么”由 Lisp 决定，“怎么画”在 Rust：

| 层 | 内容 | 放在哪 | 理由 |
|---|---|---|---|
| 平台层 | 窗口、输入、输入法、剪贴板、DPI、vsync | Rust（winit 一类） | 各平台的差异和坑很多，重写它没有扩展价值，还要先有通用 FFI |
| 文字服务 | 字体选择和回退、整形、光栅化、字形图集 | Rust（cosmic-text、swash、HarfBuzz 一类） | 工作量大、算法成熟，同样没有扩展价值；以量宽服务的形式提供给布局 |
| 场景 | 显示列表 | Lisp | 扩展性所在 |
| 光栅化 | 把显示列表画到 GPU | Rust（wgpu） | 一个图元固定、很小的渲染器 |

**渲染器有自己的线程，和 Lisp 的 GC 停顿解耦**：它一直持有最近一份显示列表，Lisp 线程在回收时，窗口照样重绘、响应缩放、动画照常进行。所以**动画是声明式的**，参照 Core Animation 和 CSS transition：Lisp 只说“光标从 A 移到 B，80 ms ease-out”“这个图层的滚动偏移变为 y”，中间帧由渲染器插值，Lisp 不必每帧运行。平滑滚动、光标滑动、滚动条淡出都属于这一类。

winit 要求事件循环在主线程上（macOS 上是强制的）。kiln-rt 已经把 Lisp 跑在另一个线程上，主线程正好留给平台层和渲染器。

**终端前端**：终端按字符格排，帧是单元格网格加光标，前端输出和上一帧的差异。它只需要写转义序列，可以用 Lisp 写，也可以是一个 Rust 宿主模块。

**进程内还是进程外**：Neovim 的 GUI 都经 UI 协议跑在另一个进程里，好处是 Lisp 侧崩溃或停在 debugger 里时窗口还活着，也能远程编辑；代价是输入法、剪贴板、平滑滚动这类交互都要跨进程往返。先做进程内的，但显示列表和输入事件的格式定成可以序列化的协议，以后同一个格式可以送到另一个进程。

#### 和 Emacs 的对照

| Emacs | KilnWorks |
|---|---|
| `fontification-functions`（jit-lock） | 装饰提供者，按区域、有缓存、有时限（“装饰提供者”） |
| mode line 的 `:eval` | mode line 提供者（纯函数） |
| `display` 属性的 `(when 条件 ...)` | 只允许声明式的数据；需要计算的情况用提供者 |
| overlay 的 `before-string`、`after-string` | 装饰数据（虚拟文本） |
| `pre-redisplay-function`、`window-scroll-functions` | 重显示前钩子，在取快照之前运行（“重显示前钩子”） |
| `posn-at-point`、按可视行移动 | 直接调用布局函数（“布局”） |
| 重显示中出错只打印一行 | 按提供者隔离，可以停用，可以调试 |
| C 写的布局和绘制 | Lisp 写的布局和场景，Rust 的平台层和光栅化（“渲染和 GUI”） |

### 在子系统入口分派

在子系统的入口放一个分派点，整个子系统都可以被重定向，而且对下游代码透明。CL 里最自然的分派点是**泛函**：
- **文件操作**：打开、保存、列目录、启动进程都经过以“位置”对象分派的泛函。远程文件、压缩文件、加密文件各是一个位置类，打开文件、目录列表、编译、搜索这些功能都不需要知道它们的存在。
- **输出目标**：kiln 的流本来就是 Gray streams，向 buffer、marker、函数输出，都只是另一个流类。
- **子进程输出**：交给一个可替换的过滤函数，默认插入 buffer 中进程 marker 所在的位置。REPL 和编译输出因此完全在 Lisp 层实现。
- **窗口放置**：所有“把某个 buffer 显示出来”的操作都经过同一个策略函数，按一张规则表决定放在哪里。用户可以统一配置“帮助总在右侧”“编译输出总在底部、不抢焦点”，包的作者不用关心布局。

泛函加方法组合同时就是 **advice 机制**：`:around`、`:before`、`:after` 方法可以由任何包添加，按类、按 buffer 类型叠加。普通函数的 advice 由 kiln 提供：全局调用都经过符号的函数格，替换函数格就对所有调用者生效（“重定义始终立即生效：依赖追踪”）。

### 状态和历史是普通数据

- **undo 历史**是普通的列表，元素是插入、删除、属性变化、marker 调整，以及“调用某个函数”的记录。树状 undo、按区域 undo 可以在 Lisp 层实现；包可以把非文本状态的变化放进 undo 历史。
- **kill ring**、按键表、选项都是 Lisp 能直接读写的数据。
- **核心的状态就是变量**：按 buffer 局部的选项（缩进宽度、折行列、模式）是 buffer 局部变量（“按上下文局部的变量”），`let` 一下就能临时改变核心代码的行为，调用方不需要传参数。

### 会产生积累的手法

下面几种手法在各个子系统里反复使用，每用一次就多一个扩展点：
1. **表代替函数**：行为参数化成一份可修改的数据（大小写表、字符宽度表、语法表、按键表、窗口放置规则、文件位置分派），并且可以按 buffer 设置、可以动态绑定。
2. **行为附着在文本位置上**：按键表、语法、只读、field、修改钩子、可见性、粘贴方式都可以挂在一段文本上，复制时跟着文本走。
3. **开放的元数据**：命令和选项是符号，任何包都能往它们的属性表上放东西（“这个命令会删除选区”“这个命令可以在搜索中执行”“这个选项的值在什么条件下安全”），元数据的作者和对象的作者解耦。
4. **在子系统入口分派**（“在子系统入口分派”）。
5. **状态和历史是普通数据**（“状态和历史是普通数据”）。

### 可塑的检视工具

参考 Pharo 上的 Glamorous Toolkit：每个对象自己定义在 inspector 里的多种视图（表格、树、图、文档、自定义面板），开发者为自己的领域对象随手加视图，而不是只看槽位列表。在这里：
- **视图是泛函的方法**，按对象的类分派，任何包都能给别人的类加视图（“会产生积累的手法” 的开放元数据）；
- 每种视图输出带属性的文本（因此可以搜索、复制、继续检视其中的对象），或者显示列表（“渲染和 GUI”）；
- debugger 的帧、REPL 的结果、后端协议返回的对象都用同一套视图。

这是活 image 相对“编辑器加外部编译器”的根本优势，作为 IDE 阶段的核心体验。

## 对 kiln 运行时的需求

### 重定义始终立即生效：依赖追踪

Emacs 的可扩展性止步于 C：C 代码直接调用的原语，advice 对它无效。KilnWorks 的核心全部是 Lisp，墙只剩 Rust runtime（GC、栈展开），扩展代码没有理由去改它。

风险在于性能优化：编译期变换、内联、编译后的 CLOS 分派（[roadmap.md](../roadmap.md) 的“性能”）都会让被优化的调用者看不到重定义，墙会悄悄回来。所以要先有**依赖追踪**（[dependencies.md](dependencies.md)）：每个优化都记下它依赖的定义，重定义时让依赖者失效并重编。这样“重定义任何东西，立即对所有调用者生效”在优化之后仍然成立。

这也是 kiln 对“动态语言难优化”的回答：不在运行期处处检查假设是否失效（那需要去优化，kiln 不做，见 [modern-practices.md](../research/modern-practices.md) 的“暂不采用”），而是在重定义时重编依赖者。

### 按上下文局部的变量

buffer 局部变量是 “状态和历史是普通数据” 的基础：一个变量在当前 buffer 有局部值，`let` 绑定它时要区分绑定的是局部值还是默认值，退出时正确恢复。

ANSI 的特殊变量只有全局值和线程内的动态绑定。在库层面模拟，就得放弃 `let`、`symbol-value` 的统一语义。kiln 可以在特殊变量机制里加一层：查找顺序为动态绑定 → 当前上下文的局部值 → 全局值。“当前上下文”对编辑器是当前 buffer，对其他程序可以是别的东西，Racket 的 parameterization 是类似的设计。这要改 `lower.lisp` 里读写特殊变量的代码和 runtime 的 TLS 方案（[abi.md](abi.md)），是 kiln 层面的功能，接口要和编辑器一起定。

### fiber

- 可重入的命令循环（“命令循环：显式的边界”）、输入框（“焦点和输入框”）：等待输入就是挂起 fiber。
- 异步任务：按需高亮、语言服务器、子进程、文件监视。
- 渲染和编辑分开：配合多线程和内存模型（[runtime-constraints.md](runtime-constraints.md) 的“待定：内存模型”），渲染线程读不可变的显示列表。
- 装饰提供者超出时限时转成异步任务（“装饰提供者”）。

这对应 [async.md](async.md) 的一次性续延，kiln 的多栈段和跨栈扫描已经是它的基础。

### debugger 和后端协议

- **扩展出错不打断编辑器**：出错的计算挂起，用户在另一个窗口里看它的帧和局部变量，选一个 restart，或者改完函数后重启某一帧。编辑器照常工作。这需要帧的调试信息（[debugging.md](debugging.md)），以及挂起计算的能力：先用同一个栈上嵌套的方式（后进先出），有了 fiber 再改成任意顺序。
- **后端协议**：按任务求值，错误返回结构化的帧和 restart，任务可以挂起和恢复。编辑器的 REPL、debugger、inspector、跳转到定义、调用者查询都走这个协议。外部工具（包括 agent）驱动 kiln 也用同一个协议。基础部分已经有了（[backend-protocol.md](backend-protocol.md)），以后在它上面扩展。

### image 和源码的同步

在活 image 里开发，image 里的定义和文件会分叉。IDE 要能列出不一致的定义，逐个写回文件或重新载入，存快照时提醒还没写回的修改。数据来自每次求值时记下的来源，和定义表、依赖追踪是同一组数据，见 [modern-practices.md](../research/modern-practices.md) 的“image 和源码的同步”。

### 系统接口

kiln 的 `kiln_rt_sys`（`rust/kiln-rt/src/rtfun.rs`）现在只有文件系统、时间和环境变量。编辑器还需要：
- 终端：raw 模式（termios）、窗口大小、`SIGWINCH`；
- 等待多个描述符：poll/epoll，和 fiber 调度器结合；
- 子进程：fork/exec 或 posix_spawn、管道、伪终端、等待和信号；
- 定时器；
- 文件监视（inotify）；
- GUI 前端：由 Rust 宿主模块提供（“Rust 宿主模块”），不经过 `kiln_rt_sys`。

### 快照、seal 和体积

- **快照**（[heap-image.md](heap-image.md)）：载入全部包后存一份，启动就是映射快照，相当于 Emacs 的 dump。
- **部分 seal**（“扩展模型和 seal”）。
- **体积**：kernel 加 CLOS 在 strip 后已有 26 MB，加上编译器是 69 MB（2026-11）。要做到常见编辑器的体积，需要 seal 时的 tree shaking 和代码体积优化：慢路径和报错路径挪到共享的桩函数，共享 undefined-function 对象，静态符号只保留需要反射的名字，压缩栈图和调用点表。体积要像性能一样有基准（[performance.md](../research/performance.md)），每次改动都能看到变化。

### Rust 宿主模块

GUI 的平台层、文字服务和渲染器都在 Rust 里（“渲染和 GUI”），和 Lisp 之间需要双向的接口：显示列表借给渲染器，布局同步调用量宽服务，命令循环等待输入事件，字体和图片以句柄的形式交给 Lisp。kiln 的 runtime 本身就是 Rust，这套接口不必走 C 的语义，见 [rust-interop.md](rust-interop.md)。它不依赖通用的 C FFI，也不依赖 fiber，可以先于它们做。

### 显示管线需要的

- **持久化的文本结构**：快照的代价要是常数级（“重显示前钩子”），渲染线程和后台任务可以同时读。
- **运行期的依赖追踪**：装饰提供者的缓存按它读过的区域和变量失效，把 [dependencies.md](dependencies.md) 推广到运行期数据，类似 Salsa 的增量计算。
- **性能**：布局和装饰提供者都是 Lisp，每次重显示都要运行。现在 `format`、流和 CLOS 的速度（[performance.md](../research/performance.md)）撑不起交互式编辑。

## 扩展模型和 seal

完全开放的问题是没有稳定的契约：一切都能改，于是任何内部函数都可能被某个扩展依赖，核心一改就坏。只暴露登记过的选项和命令，契约清楚，但用户会撞到墙。KilnWorks 用 seal 让这件事可以逐项选择：
- **开发期**：完全开放的活 image，KilnWorks 自己和它的扩展都在里面开发。
- **发行版**：核心部分 seal，整体优化、裁剪。**声明的扩展点**保持开放：可以重定义或 advice 的函数、可以加方法的泛函、用户选项、钩子。核心只在这些点上调用扩展代码。
- **扩展的执行方式**：
  - 默认用共用前端的 HIR 求值器执行。发行版可裁剪原生编译入口和 Cranelift；扩展调用的是 seal 过的原生核心，热路径仍是机器码。
  - 需要原生性能的扩展：编译器模块和 Cranelift 作为可选的附加部分，按需映射进来（快照已经能处理固定地址的附加代码和数据，[heap-image.md](heap-image.md) 的“设计”）。

声明的扩展点就是 KilnWorks 的公开 API。某个函数从封闭改成开放，只是 seal 清单里的一行，不需要像“C 核心加脚本语言”那样用另一种语言重写。这也回答了 [positioning.md](positioning.md) 待定问题里“seal 的粒度”：至少要支持“整个程序 seal，但列出的定义保持开放”。

## 代价

可扩展性有代价，要提前接受或者规避：
- **一切影响一切**：任何函数都可能被重定义，任何选项都可能被动态绑定。核心代码要按这个前提写，测试要覆盖扩展点被替换的情况。
- **性能**：靠依赖追踪和 seal，而不是放弃动态性（“重定义始终立即生效：依赖追踪”、“扩展模型和 seal”）。
- **契约**：声明的扩展点是契约，没有声明的内部函数不是。开发期也要能看到这条界线，例如重定义一个未声明为扩展点的函数时给出提示。
- **积累的承诺**：每一张可修改的表、每一个分派点，都是一份长期的 API 承诺。加之前要有具体的需求。

## 待定问题

- 名字。
- 文本的数据结构：gap buffer、rope 还是 piece table？要考虑多光标、大文件、undo，以及快照的代价和并发读（“重显示前钩子”）。倾向持久化的 rope。
- 按上下文局部的变量：语义（`let` 绑定局部值还是默认值）、实现（加在 TLS 方案的哪一层）、和 fiber 切换的关系。
- 命令和选项的元数据放在符号属性表上，还是用专门的命令对象？
- 后端协议的格式：S 表达式还是 JSON？只在进程内，还是也走 socket？
- 扩展点的声明方式：用 `declaim`，还是在定义处标注？
- 显示列表和输入事件的具体编码；图元集合的边界（图片、矢量路径要不要放进第一版）。
- 装饰提供者的时限怎么定：固定值，还是按帧的剩余时间分配？
- 量宽服务的接口：按字形串一次一问，还是成批提交？缓存放在 Lisp 侧还是前端？
- 声明式动画的词汇：哪些属性可以过渡，缓动曲线怎么指定。
