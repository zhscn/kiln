# 编译器架构

编译器分为 Lisp 语义前端、Rust MIR 中端和 Cranelift 机器后端。Lisp 负责需要执行 Lisp 代码和查询编译环境的工作；Rust 在封闭的语义输入上构造控制流、分析、优化和选择表示。Rust interop 与编译协议是这一划分的基础设施。

这是确定的目标架构。当前实现仍由 Lisp 将 HIR 分析并降级为 KIR，Rust `kiln-cg` 接手代码生成；MIR、结构化 HIR 交接和安全 interop 封装尚未实现。迁移期间保留现有路径作为行为参照，各项迁移完成后移除对应的旧分析和降级代码。

## 阶段与职责

```text
源码 → reader / CST → 宏展开、编译环境、绑定与声明 → HIR
                         Lisp                         │
                编译期执行 ↔ HIR 求值器               │ 批量语义交接
                                                      ↓
                         Rust                  MIR：CFG + SSA
                                                      ↓ 分析与优化
                                               表示选择、ABI 降级
                                                      ↓
                                                    KIR
                                                      ↓ kiln-cg
                                              Cranelift → JIT / AOT
```

| 层 | 负责 | 输出契约 |
|---|---|---|
| Lisp 前端 | 顶层处理、宏和编译器宏、编译期执行、词法与全局环境、绑定身份、声明与类型展开 | 已解析语义的 HIR、来源、依赖和常量描述 |
| Lisp HIR 求值器 | 编译期宏函数及辅助函数的执行、解释执行入口 | Lisp 值及受语言规定的副作用 |
| Rust MIR | 控制流、标量 SSA、类型与调用摘要、内联、逃逸和别名分析、表示选择 | 验证过的低级 KIR 及代码元数据 |
| kiln-cg / Cranelift | 调用约定实现、异常表、栈图、机器优化、寄存器分配、目标代码 | 可安装的 JIT 代码或目标文件 |
| runtime 与安装层 | GC roots、代码和常量生命周期、依赖验证、定义发布、错误和非局部退出 | 对活 image 可见的函数和定义 |

HIR 是语义树，MIR 是保留 Lisp 抽象操作的控制流图，KIR 是带对象布局与调用约定的低级 IR。MIR 的 SSA 服务于 Lisp 特有的分析：对象身份、闭包、可写捕获、多值和动态退出仍可辨认。Cranelift 继续负责机器层的通用优化。

## 语义边界

进入 Rust 前，宏、编译器宏、类型展开和编译环境查询已经完成。这里的“编译期执行完成”指语言要求的编译期效果，不是先求值普通函数体。普通程序的动态调用、类型检查和副作用保留为 IR 操作。

Lisp 导出绑定后的函数、捕获关系、声明作用域、源码位置、策略、可用内联体和依赖假设。Rust 不保存 Lisp 环境，也不在优化过程中逐节点回调宏函数或 `subtypep`。不能归一化为受支持事实的类型保留运行期检查；没有内联体的调用保持普通调用。

全局函数在活 image 中保持可重定义语义。静态调用、内联和布局特化必须有语言保证、守卫或可验证的依赖；seal 提供更强的冻结契约。守卫失败走显式普通路径，不依赖尚未设计的优化帧反优化机制。

## 组件依赖

Lisp 保留 reader、CST、环境协议和语义 HIR。Rust 目标组件按以下方向依赖，名称表示计划中的组件边界：

- `kiln-interop`：runtime 服务的安全 Rust 封装、root 与回调边界。
- `kiln-mir`：纯 Rust IR、验证器、分析和降级；不依赖 Lisp 堆对象或运行中的 image。
- `kiln-compiler`：导入请求、组织 MIR 和代码生成、返回产物；通过 interop 与 image 安装层连接。
- 已有 `kiln-cg`、`kiln-rt` 和 launcher：机器后端、运行时与链接入口。

协议样本、验证器和独立 Rust 驱动让两侧可以分别实现和测试。编译器首先使用 interop；GUI、动态 Rust 模块、异步回调和项目工具随后复用基础设施，不作为编译器接入的前提。

## 接入顺序

1. 实现 interop 的服务表、作用域 roots、缓冲区所有权、错误与回调退出边界，建立独立边界测试。
2. 固定 HIR 导出协议和验证器，提供 SBCL 与 kiln 两个适配器及可重放的请求样本。
3. 实现 MIR 构造、验证和保守的 MIR → KIR 路径，先保持语义与既有 ABI。
4. 按分析职责迁移类型传播、调用摘要、内联、身份与逃逸证明、机器值和存储选择，逐项移除 Lisp 中的对应实现。
5. 在稳定边界上增加缓存、纯 Rust 工作并行、跨函数优化及 seal/WPO。

验证覆盖宿主和 image 两种前端、HIR 求值与原生执行、JIT/AOT、GC 压力、非局部退出、调试信息及自举确定性。ANSI 差分使用 SBCL 的已知失败与跳过基线，同时保留项目自身的语义回归；迁移不能扩大差异。

详细契约见 [HIR](hir.md)、[MIR](mir.md)、[编译协议](compiler-protocol.md)、[降级](lowering.md) 和 [Rust interop](rust-interop.md)。
