# 编译延迟与迭代效率

编译器自身的性能以缩短编辑、编译、验证的反馈时间为目标。分别测量冷启动、活 image
中的首次编译、重复编译与重定义后的增量编译；生成程序的运行速度另行衡量。

## 测量边界与方法

`tools/bench-compiler.py` 使用已有的自举可执行文件和模块清单，在独立目录中执行
一次预热和五次测量，报告墙钟时间、进程峰值 RSS，以及各模块的前端、降级和 KIR
输出时间。默认使用固定 8 GiB 堆；保留调用者指定的 `MMTK_GC_TRIGGER`。
前端计时包含会话准备、读入、编译期求值、宏展开、HIR 构造及其分析；降级计时包含
模块生成；输出计时包含文件打开和关闭。这些是阶段边界计时，不能代替热点采样。
原始日志、逐次数据和中位数保存在输出目录，便于检查波动并比较改动前后结果。
脚本还记录可执行文件与模块清单的校验和，用于识别测量对象；相同输入产生
不同 KIR 的运行会被拒绝。

```sh
tools/bootstrap.sh
tools/bench-compiler.py --output build/compiler-baseline
# 修改后重新自举，再使用另一个输出目录测量。
tools/bench-compiler.py --output build/compiler-candidate
```

测量时不同时运行自举、端到端测试或其他 CPU 密集任务。比较同机、相同堆配置和
相同输入；重复测量区分噪声与收益。性能报告同时保留时间和内存，避免把峰值
内存增长隐藏在加速中。

这项基准只执行 Lisp 编译器到 KIR，包含进程启动与初始化；不包含 Cranelift
代码生成和系统链接。后续增加原生 `compile`、源文件 `load`、FASL 加载和宏重定义
场景，单独测量首次与缓存命中的延迟，再细分读入、宏展开和 HIR 分析成本。

## 优化流程

1. 先运行阶段基准，用 CPU 和分配 profile 确认热点。
2. 减少热点中的临时列表、重复遍历和重复查询。工作队列采用可增长向量或双端队列；
   有紧凑编号的集合采用位集合，分析结果采用索引向量。仅在小集合上使用线性查找。
3. LIR 从首期使用结构化内存交接和规范化二进制文件；分别测量编码、复制、解码和验证成本。文本 dump 只用于诊断，对象引用跨边界遵守 roots 和移动规则。
   目标设计里交接的是 LIR（[lir.md](lir.md)），阶段计时相应拆成 HIR、MIR 构造和分析、
   LIR 输出，以及 kiln-cg 的 LIR 降级和代码生成。
4. 按访问模式试验紧凑节点编号、字段数组和分析侧表。向量中的对象引用并不意味着
   节点本体连续；用缓存命中、分配量和端到端时间决定布局。
5. 对不可变类型描述和签名采用会话级 interning。明确共享范围和退出生命周期，
   避免活 image 中的全局池永久保留历史编译数据。
6. 在已有依赖追踪上扩展按需分析与缓存。区分纯分析和有副作用的编译期执行，
   将宏、声明、内联定义与布局变化纳入失效条件，控制缓存内存预算。

Rust 编译器的 arena、interning、索引容器和 query 系统是实现参考。CL 的对象身份、
可修改性、动态重定义和编译期副作用仍是约束。批量生命周期管理需要明确逃逸规则
与 GC 集成；单纯把对象收集到一个向量不能实现批量释放。内部数据表示可以专门化，
公开的 ANSI 容器行为保持不变。

局部类型传播、拆箱和逃逸分析主要提高生成程序的效率；若它们也降低自编译开销，
以同一组基准单独验证。新增分析的编译成本也计入迭代延迟。

HIR 的表示与分析见 [hir.md](hir.md)，降级见 [lowering.md](lowering.md)，
reader 与文件流见 [io.md](io.md)。性能测量记录见
[performance.md](../research/performance.md)。

宿主的可移植编码器按记录构建临时列表，image 的批量 native 编码器从程序快照生成同一字节格式；一次性 `compile` 直接交接 Rust 自有记录，省去字节向量及编码、解码往返。结果仍使用 Lisp simple-vector octets，记录空间与编码成本须单独测量，不能将传输实现等同于预算达标。运行期缓存和 FASL 不再依赖 KIR 文本。

## 小函数与切换预算

运行期 CLOS 判别函数、有效方法和构造器是独立的编译延迟场景，不能仅以整模块吞吐判断协议成本。测量预热后的单函数编译，分别报告中位数、尾延迟、协议字节数、复制量、Rust 分配和总编译时间；将 GC 压力、缓存命中与未命中分开。

小函数入口复用后端会话与分配容量，批量提交连续记录，只编码本次函数需要的常量与来源。保留内存 KIR，不经文本打印、临时文件或子进程。必需校验始终执行，调试模式可额外启用昂贵的不变量检查。

初始工程预算为：预热后不超过 100 个 LIR 操作的小函数，编码、复制、解码和结构验证合计中位数不超过 100 微秒，且不超过总原生编译中位数的 10%。这些是待验证目标，不是现有测量结果；未达到时先定位固定成本，再决定调整预算或实现。

生产切换以同机、同配置的旧路径为基线：小函数编译和完整自编译中位数回退不超过 5%，运行期基准几何平均回退不超过 2%，单项稳定回退超过 5% 必须解释并处理后再决定切换。重复测量确认噪声，基准范围包括 cl-bench、Benchmarks Game 与实际 CLOS 编译。实验路径允许回退，默认路径不得以未来优化承诺替代测量。

## 小函数基准入口

`tools/bench-native-compile.py --modules build/boot/stage0 --output build/native-baseline` 使用指定目录的五个模块，测量预热后独立小函数的原生 `compile` CPU 时间。`bench/native-compile-small.lisp` 每次生成新函数并校验调用结果，绕开顶层产物缓存；每个进程先预热，重复进程报告中位数。比较不同模块目录时保持同一后端、堆配置和机器负载，运行期间不进行构建或其他基准。原始输出保存在指定的忽略目录。它覆盖完整小函数编译开销，不代替协议阶段的独立计时。
