# 编译延迟与迭代效率

编译器自身的性能以缩短编辑、编译、验证的反馈时间为目标。分别测量冷启动、活 image
中的首次编译、重复编译与重定义后的增量编译；生成程序的运行速度另行衡量。

## 测量边界与方法

`tools/bench-compiler.py` 使用已有的自举可执行文件和模块清单，在独立目录中执行
一次预热和五次测量，报告墙钟时间、进程峰值 RSS，以及各模块的前端、降级和二进制记录
输出时间。默认使用固定 8 GiB 堆；保留调用者指定的 `MMTK_GC_TRIGGER`。
前端计时包含会话准备、读入、编译期求值、宏展开、HIR 构造及词法准备；降级计时包含
模块生成；输出计时包含文件打开和关闭。这些是阶段边界计时，不能代替热点采样。
原始日志、逐次数据和中位数保存在输出目录，便于检查波动并比较改动前后结果。
脚本还记录可执行文件与模块清单的校验和，用于识别测量对象；相同输入产生
不同编译记录的运行会被拒绝。

`--pipeline mir` 显式选择本次自编译的分析路径，并写入汇总；省略时使用
`KILN_BUILD_PIPELINE`，环境变量也未设置时选择 MIR。工具保留 `--pipeline hir`，
用于测量仍支持 HIR 原生编译的旧版本；当前编译器仅接受 MIR。比较不同构建的
可执行文件时应显式指定各自支持的路径，避免把模块自身的编译路径与本次测量
使用的路径混为一谈。

```sh
tools/bootstrap.sh
tools/bench-compiler.py --output build/compiler-baseline
# 修改后重新自举，再使用另一个输出目录测量。
tools/bench-compiler.py --output build/compiler-candidate
```

测量时不同时运行自举、端到端测试或其他 CPU 密集任务。比较同机、相同堆配置和
相同输入；重复测量区分噪声与收益。性能报告同时保留时间和内存，避免把峰值
内存增长隐藏在加速中。

这项基准执行 Lisp 编译器到二进制后端请求，包含进程启动与初始化；不包含 Cranelift
代码生成和系统链接。指定 `--backend target/release/kiln-cg` 后，在每次模块编译结束后
分别生成各模块的目标文件，另报后端墙钟时间、Cranelift 机器码编译时间和目标文件字节数。
LIR 字节数与 `lir_metrics` 始终记录；目标文件测量后删除，后端原始计时保留在日志中。
`tools/lir_stats.py FILE.lir...` 按规范化 LIR 的函数与基本块统计变量、语句、赋值和
显式 poll，并单列常量个数及包的记录、边和字符串占用。统计只遍历函数的代码块，
不把常量中的 Lisp 形式当成指令。比较代码膨胀时同时检查这些数量和文件字节数，
因为常量与调试数据也占用二进制包，而退出 SSA 的复制和 poll 可能显著减少，
却只改变总文件的一小部分。
已有模块可用 `--lir-directory DIR --backend target/release/kiln-cg` 独立测量，
避免在后端采样中重复运行 Lisp 编译器。跨版本比较固定同一个后端二进制，使用
`machine_seconds` 区分 Cranelift 优化与寄存器分配成本，使用后端总时间观察
解码、LIR 降级、调试信息和目标文件输出的额外成本。

后续增加原生 `compile`、源文件 `load`、FASL 加载和宏重定义
场景，单独测量首次与缓存命中的延迟，再细分读入、宏展开和 HIR 词法准备与 MIR 分析成本。

## 运行期编译的阶段计时

编译器可在调用者动态绑定的 `kiln.compiler::*compilation-metrics*` 哈希表中记录
阶段耗时，默认关闭。各项包含墙钟、进程 CPU 时间、排除嵌套阶段后的自身耗时、
调用次数及计时单位。编译期求值可能递归调用编译器，因此各阶段的包含耗时不能
直接相加；自身耗时用于归因，最外层的实际操作耗时用于判断迭代延迟。

计时覆盖前端、MIR 构造、优化、分析的实际计算、MIR 到 LIR 的发射、LIR 规范化与
编码，以及后端请求。命中分析缓存的查询不计为分析计算；后端内部的 Cranelift
时间仍由 `KILN_TIME` 单独记录。开启计时会增加时钟查询和统计开销，比较样本时
保持相同设置，热点采样与未开启计时的端到端测量用于交叉核对。

## 优化流程

1. 先运行阶段基准，用 CPU 和分配 profile 确认热点。
2. 减少热点中的临时列表、重复遍历和重复查询。工作队列采用可增长向量或双端队列；
   有紧凑编号的集合采用位集合，分析结果采用索引向量。仅在小集合上使用线性查找。
3. LIR 从首期使用结构化内存交接和规范化二进制文件；分别测量编码、复制、解码和验证成本。文本 dump 只用于诊断，对象引用跨边界遵守 roots 和移动规则。
   生产交接使用 LIR（[lir.md](lir.md)），阶段计时相应拆成 HIR、MIR 构造和分析、
   LIR 输出，以及 kiln-cg 的 LIR 降级和代码生成。
4. 按访问模式试验紧凑节点编号、字段数组和分析侧表。向量中的对象引用并不意味着
   节点本体连续；用缓存命中、分配量和端到端时间决定布局。
5. 对不可变类型描述和签名采用会话级 interning。明确共享范围和退出生命周期，
   避免活 image 中的全局池永久保留历史编译数据。
6. 在已有依赖追踪上扩展按需分析与缓存。区分纯分析和有副作用的编译期执行，
   将宏、声明、内联定义与布局变化纳入失效条件，控制缓存内存预算。

Rust 编译器的 arena、interning、索引容器和 query 系统是实现参考。CL 的对象身份、
可修改性、动态重定义和编译期副作用仍是约束。批量生命周期管理需要明确逃逸规则
与 GC 集成；单纯把对象收集到一个向量不能实现批量释放。内部数据表示可以专门化，
公开的 ANSI 容器行为保持不变。

局部类型传播、拆箱和逃逸分析主要提高生成程序的效率；若它们也降低自编译开销，
以同一组基准单独验证。新增分析的编译成本也计入迭代延迟。

SSA 参数化简对转发链做路径压缩，避免每条入边重复追踪同一条长链；没有受保护的
类型细化参数时，直接使用第一次化简结果。谓词与条件边改写先从同一份单元摘要
收集一轮计划，再执行改写；下一轮重新求摘要，使新事实继续传播。逐函数修改后
立刻查询单元摘要会使未修改函数也反复参与固定点计算，因此批次边界是复用分析的关键。

HIR 缓冲区的存储声明为 simple-vector，计数及 MIR 的编号、种类和位置声明为
fixnum，使宿主编译器能专门化这些频繁读取的元数据。对象集合与支配集合仍可使用
任意精度整数，不能套用编号的表示限制。目标端结构访问器通过槽声明约束读取
结果，并在构造和写入时检查类型，使内联后的 MIR 也能利用相同事实；宿主和
原生编译器的收益仍分别测量。

HIR 的词法语义见 [hir.md](hir.md)，MIR 分析见 [mir.md](mir.md)，降级见 [lowering.md](lowering.md)，
reader 与文件流见 [io.md](io.md)。性能测量记录见
[performance.md](../research/performance.md)。

宿主的可移植编码器使用可增长的紧凑记录、边与字节向量，image 的批量 native 编码器直接构造拥有所有权的记录并生成同一字节格式；一次性 `compile` 直接交接 Rust 自有记录，省去字节向量及编码、解码往返。结果仍使用 Lisp simple-vector octets，记录空间与编码成本须单独测量，不能将传输实现等同于预算达标。运行期缓存和 FASL 不再依赖 KIR 文本。

## 小函数与切换预算

运行期 CLOS 判别函数、有效方法和构造器是独立的编译延迟场景，不能仅以整模块吞吐判断协议成本。测量预热后的单函数编译，分别报告中位数、尾延迟、协议字节数、复制量、Rust 分配和总编译时间；将 GC 压力、缓存命中与未命中分开。

当前小函数编译批量提交结构化程序，每次建立后端模块，不经过文本、临时文件或子进程。后端会话及分配容量复用仍是优化方向。必需校验始终执行，开发期可以额外启用 MIR pass 契约审计。

初始工程预算为：预热后不超过 100 个 LIR 操作的小函数，编码、复制、解码和结构验证合计中位数不超过 100 微秒，且不超过总原生编译中位数的 10%。这些是待验证目标，不是现有测量结果；未达到时先定位固定成本，再决定调整预算或实现。

性能优化以同机、同配置的旧路径为基线：小函数编译和完整自编译中位数回退不超过 5%，运行期基准几何平均回退不超过 2%；单项稳定回退超过 5% 时，定位原因并记录处理结果。重复测量确认噪声，基准范围包括 cl-bench、Benchmarks Game 与实际 CLOS 编译。这些预算仍需通过独立测量验证，默认管线的选择不表示性能预算已经达标。

## 小函数基准入口

`tools/bench-native-compile.py --modules build/boot/stage0 --output build/native-baseline` 使用指定目录的五个模块，测量预热后独立小函数的原生 `compile` CPU 时间。`bench/native-compile-small.lisp` 每次生成新函数并校验调用结果，绕开顶层产物缓存；每个进程先预热，重复进程报告中位数。比较不同模块目录时保持同一后端、堆配置和机器负载，运行期间不进行构建或其他基准。原始输出保存在指定的忽略目录。它覆盖完整小函数编译开销，不代替协议阶段的独立计时。

`--pipeline hir|mir` 在预热之前设置运行期编译路径，不由模块目录的构建方式推断；
默认规则与自编译基准一致。`--backend` 选择后端可执行文件，默认使用 debug 构建；
测量生产配置时可指定 `target/release/kiln-cg`。默认堆为 8 GiB，保留调用者的
`MMTK_GC_TRIGGER` 设置。汇总包含路径、堆、后端和模块校验和，以及原基准、
生成的源程序和 LIR 校验和。每个样本是一次进程内多次编译的平均 CPU 时间，
报告的是这些均值的中位数，不提供单次编译的尾延迟分布。

HIR → MIR 的阶段对照和原生编译测量见
[2026-11-16 测量](../research/mir-compilation.md)；分析复用与原生代码成本见
[2026-11-17 测量](../research/mir-analysis-optimization.md)。
