# 推测、守卫和失效：通用的特化框架（草案）

开发期的 kiln 保留 CL 的全部动态性：类可以重定义，方法随时增删，函数和类型可以重新定义，实例可以 `change-class`。性能靠的是在这些动态性之上加快路径。到目前为止，这些快路径是一个一个手写的，每个都自己决定缓存什么、自己负责失效。本文把它们统一成一个模型，作为以后添加快路径的基础设施，并把同一套依赖也用于编译结果的缓存和交付期的 seal。

状态：**待定**。下面的“现状”是已有的代码；“模型”和“实施步骤”是计划。

## 现状：各自为政的缓存

这几轮性能优化加的快路径，几乎都是同一种做法：按观察到的情况记下结果，用一个便宜的检查确认它仍然适用，在某些定义变化时清掉。

| 快路径 | 键 / 守卫 | 依赖的假设 | 失效方式 |
|---|---|---|---|
| 判别闭包的缓存（单分派、双分派） | 参数的 stamp | 泛函的方法集、类层次 | 增删方法、类重定义时重算判别函数（`forget-call-caches`，`lisp/target/clos/redefinition.lisp`） |
| 读函数融合：缓存项是槽的位置 | stamp | 类的槽布局 | 类重新 finalize 后 stamp 变了，旧项自然不再命中 |
| `make-instance` 的快路径 | 类的 unique number 和 `*construction-epoch*` | 类没有用户定义的初始化方法、initarg 集合不变 | 增删相关方法时增加 epoch（`lisp/target/clos/constructors.lisp`） |
| 方法函数槽的位置 | 方法对象的槽列表 | 方法类的槽布局 | 每次调用都比较槽列表（检查式守卫） |
| `slot-value` 的全局缓存 | （类，槽名） | 槽布局 | 类重定义 |
| `typep` 的全局表 | （stamp，类型说明符） | 类层次、`deftype` 的定义、`find-class` 的映射 | `invalidate-type-caches`：`deftype`、`(setf find-class)`、类重新 finalize |
| 调用点上的单项 `typep` 缓存 | stamp | 同上 | 没有主动失效：被淘汰的实例在这个调用点上可能拿到旧类的答案，直到分派更新它（已知限制） |
| Iconoclast 的遍历计划、AST 子节点的计划 | AST 的类 | AST 类不会被重定义 | 从不失效（隐含的假设） |
| 内联函数、宏、setf 展开器、常量 | — | 定义不变 | 依赖追踪：重新求值依赖者（`lisp/target/compiler/dependencies.lisp`） |

问题：

- **重复**：每个缓存都有自己的版本号或清除函数，规则散在各处。
- **容易漏**：`typep` 的全局表一开始就漏了类重定义；调用点缓存至今对被淘汰的实例有已知的过时问题；AST 计划依赖的假设没有写出来。
- **无法统一处理**：seal 时本应把这些假设一次性固定下来、把守卫和通用路径去掉，但现在没有一个地方列出“kiln 推测了哪些事”。

## 模型

三个概念：假设、守卫、失效。

### 假设

假设是一个**有名字、带版本的事实**。名字沿用依赖追踪的键（`(KIND NAME)`），新增的种类：

| 键 | 事实 |
|---|---|
| `(:class C)` | 类 C 的布局（槽的位置）、优先级列表、是否 finalize |
| `(:methods G)` | 泛函 G 的方法集和方法组合 |
| `(:initialization C)` | 和 C 的实例初始化有关的方法集（`initialize-instance`、`shared-initialize`、`allocate-instance` 等对 C 适用的方法），以及 C 的默认 initarg |
| `(:type NAME)` | `deftype` 的展开、`find-class` 的映射 |
| `(:function F)`、`(:macro M)` 等 | 依赖追踪已有的种类 |

每个假设对应一个**版本格**（一个 fixnum）。事实改变时版本加一。

### 守卫

守卫是特化代码或缓存项在使用前做的便宜检查，两种：

- **检查式**：比较一个对象自带的标记，例如参数的 stamp、版本格的值。每次使用都要一次载入和比较，但不需要登记，也不怕漏通知。适合以对象为键的缓存（分派、`typep`、槽位置）。
- **推送式**：特化代码本身不检查，而是把自己登记为假设的依赖者；假设改变时由失效过程把它撤掉（清空缓存、把调用入口换回通用路径）。快路径上零开销，但需要登记表，也需要保证所有改变都经过通知。适合全局的事实（方法集、`deftype`），以及守卫开销要紧的地方（内联的槽访问）。

**倾向**：以对象为键的用检查式；全局事实用推送式，并在实现里集中到一个“改变假设”的函数上，所有修改类、方法、类型的入口都经过它。

### 失效

把依赖追踪的“依赖者”推广成三种：

1. **定义单元**（已有）：重新求值。
2. **缓存**：清空或丢弃对应的项。
3. **特化代码**：把调用入口换回通用版本；下次需要时再重新特化。

**约束**：

- 每个特化都必须有一条通用路径可以退回。守卫失败时走通用路径，而不是报错。
- 失效只影响之后的调用。正在执行的帧继续用旧代码，和 CL 对重定义的语义一致（重定义在下一次调用时生效）。因此不需要栈上替换（OSR）或去优化。所有特化都放在函数入口或调用点上。
- 登记表不能让依赖者永远活着：被丢弃的闭包、编译好的代码要能被 GC 回收。这需要弱引用，或者按代际批量清理（见“待定”）。

## 用生成的代码代替手写的闭包

现在的分派用宏展开出一族闭包（1–6 个参数、每个特化位置一份），有效方法用闭包组合起来。这能工作，但每种新形态都要手写一组闭包，而且闭包之间无法内联。

有了统一的假设和失效之后，判别函数、有效方法、`make-instance` 的构造器都可以**生成代码**：

- 用原生 `compile` 在运行期编译；或者像 SBCL 的 PCL（`dlisp.lisp` 加构建期预编译）那样，把常见形态做成模板，构建时预先编译好，运行期只需填参数。
- 生成的代码把各个假设当常量用（槽的位置、下一个方法、initarg 的处理），并把这些假设登记为依赖。
- 编译太慢的场合（只调用几次的泛函）仍用闭包，靠调用计数决定何时生成代码，也就是分层编译。

## 编译结果的缓存

同一套依赖也适用于编译器本身：一个顶层形式的编译结果，取决于形式本身、当时的包，以及它在编译期用到的定义（宏、内联函数、setf 展开器、常量、类型）。依赖追踪已经记下了后者。

- 键：形式内容的哈希、包、所依赖的各个假设的版本。
- 值：KIR，或者机器码。
- 用途：重新 `load` 一个只改了一处的文件，或者重新构建模块时，只重编内容变了、或依赖变了的形式。
- 前提：编译是确定的（前端已经保证了这一点，见 [front-end.md](front-end.md)），宏展开没有副作用。编译期有副作用的形式（`eval-when` 的编译期部分、定义宏）要把副作用作为输出记下来，命中缓存时照样重放，和依赖追踪记录“输出”的做法一样。

参考：

- Zig 的增量编译，见 [zig-incremental.md](../research/zig-incremental.md)。
- Kirisame 等人的 shortcut memoization（*Incremental Live Programming via Shortcut Memoization*，2026，arXiv 2603.19560）。它在解释器的重写步骤上做记忆化，不适合原生代码和有副作用的 CL 程序；但“从旧版本的执行中学习可复用的片段，结构相似也能命中”的思路可以用在形式一级的缓存上。

## seal：把假设固定下来

seal（[positioning.md](positioning.md)）之后，被 seal 的定义不再改变。对本框架来说，这意味着：

- 涉及被 seal 定义的假设，版本格变成常量：检查式守卫在编译期折叠掉，推送式的登记直接省掉。
- 通用路径、登记表、版本格，只要没有未 seal 的代码还需要，就被 tree shaking 去掉。
- 假设的清单正好回答了“seal 允许编译器假定什么”：单实现的泛函变成直接调用，访问函数变成按固定下标读槽，`make-instance` 变成直接分配，`typep` 变成常量或 stamp 比较。
- 保持开放的定义（编辑器要求的“整个程序 seal，但列出的定义保持开放”）保留守卫和通用路径。

开发期和交付期因此是同一份特化代码：开发期带守卫，交付期去掉守卫。

## 实施步骤

1. **假设登记表和版本格**：实现假设的键、版本格和集中的“改变假设”入口。把现有的 `*construction-epoch*`、`invalidate-type-caches`、`forget-call-caches` 改为通过它工作。这一步是纯重构，要求自编译时间不变、测试全过。
2. **补上已知的漏洞**：调用点的 `typep` 缓存改为检查版本格；AST 计划的“类不会被重定义”写成显式的假设。
3. **调用点特化**：lowering 在 CLOS 调用点生成内联缓存；方法体里对特化参数的、槽名为常量的 `slot-value`，按 PCL 置换向量的方式取槽的位置；类名和 initarg 名都是常量的 `make-instance` 调用改写成调用构造器对象。三者都用检查式守卫，依赖登记在假设上。
4. **生成代码**：判别函数、有效方法、构造器改由模板生成代码，按调用计数分层。
5. **编译结果的缓存**：形式一级，先用于 `load` 和构建程序。
6. **seal 时折叠**：和 seal 的实现一起做。

每一步都按 profile 衡量收益：步骤 1 和 2 不求收益，求正确；步骤 3 起各自要有测量。

## 待定

- **弱引用**：登记表需要 MMTk 的弱引用支持，或者用代际清理（假设改变时整批丢弃，而不是逐个注销）。倾向后者，先不依赖弱引用。
- **多线程**：现在只有一个 Lisp 线程。有了多线程之后，失效和特化代码的安装要有内存序的保证（守卫读版本格、安装方发布新入口）。这与 [runtime-constraints.md](runtime-constraints.md) 的内存模型一起考虑。
- **假设的粒度**：`(:class C)` 是一个版本格，还是布局、优先级列表各一个？粒度太粗会导致不必要的失效（例如给 C 定义一个子类，C 自己的布局没变，依赖 C 的特化代码却都失效了）。先粗后细，按实际的失效频率调整。
- **缓存的内存上限**：特化代码和编译结果缓存都需要回收策略。
